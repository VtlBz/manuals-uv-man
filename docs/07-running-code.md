## uv run - запуск в контексте проекта

Команда `uv run` - основной способ выполнения кода и инструментов в проекте,
управляемом `uv`. Она гарантирует, что команда выполняется в правильном
виртуальном окружении с актуальными зависимостями.

### Что происходит при вызове uv run

При каждом вызове `uv run` выполняется следующая
последовательность:

1. Находит ближайший `pyproject.toml`, поднимаясь от текущей
  директории запуска вверх по дереву каталогов.
2. Проверяет, актуален ли `uv.lock` относительно `pyproject.toml`.
  Если нет - обновляет разрешение зависимостей и lock-файл.
3. Проверяет, существует ли `.venv` и соответствует ли он `uv.lock`.
  Если окружение отсутствует или устарело - создает его или
  доустанавливает недостающие пакеты.
4. Подбирает версию Python с учетом `.python-version`
  и `requires-python`.
5. Запускает указанную команду в контексте окружения.

Таким образом, одна команда заменяет ручную цепочку:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python main.py
```

Вам не нужно помнить о `uv sync` - он вызывается автоматически при каждом `uv run`.

### Базовые сценарии

```bash
# Запуск Python-скрипта
uv run python app.py

# Запуск установленного CLI-инструмента (например pytest, ruff)
uv run pytest

# Запуск Python-модуля
uv run python -m mymodule

# Запуск inline Python-кода
uv run -- python -c "print('hello from uv')"

# Запуск с аргументами для скрипта
uv run python app.py --port 8080 --debug
```

### `uv run` vs ручная активация `.venv`

| Критерий | Активация `.venv` | `uv run` |
| -------- | ----------------- | -------- |
| Синхронизация | Вручную (`uv sync`) | Автоматическая |
| Изоляция | Создание venv вручную | Автоматическое |
| Скорость | Мгновенный запуск | Проверка lock (~мс) |
| Переносимость | Зависит от shell | Единый интерфейс |
| CI/Docker | Нужна цепочка команд | Одна команда |
| IDE | Стандартная интеграция | Указать `.venv/bin/python` |
| Когда нужна активация | Долгая интерактивная сессия | - |

В большинстве случаев `uv run` предпочтительнее. Ручная активация может
быть удобна при длительной интерактивной работе в shell, когда набирать
`uv run` перед каждой командой неудобно.

### Пропуск синхронизации

Если вы уверены, что окружение актуально, синхронизацию можно отключить
для ускорения запуска:

```bash
# Пропустить проверку синхронизации зависимостей
uv run --no-sync pytest
```

Это полезно в ситуациях, когда вы запускаете команду много раз подряд и не
хотите тратить время на проверку lockfile при каждом вызове.

### Запуск с дополнительными зависимостями

Иногда нужно временно добавить пакет для одного запуска, не внося его в
`pyproject.toml`:

```bash
# Временно добавить пакет только для этого запуска
uv run --with rich python -c "from rich import print; print('[bold green]Hello![/]')"

# Несколько временных пакетов
uv run --with rich --with httpx python script.py
```

Флаг `--with` работает по модели наложения (overlay): временные пакеты
устанавливаются поверх существующего окружения проекта. Скрипт видит
и зависимости проекта, и дополнительные пакеты из `--with`. После завершения
команды overlay исчезает, `pyproject.toml` и `uv.lock` не изменяются.

Это полезно для экспериментов, одноразовых отладочных запусков и проверки
совместимости с библиотекой, которую пока не нужно добавлять в проект.

!!! note "Разделитель --"
    Используйте `--` (двойное тире) для явного разделения аргументов `uv run` и
    аргументов запускаемой команды. Это особенно важно, если команда принимает
    флаги, которые uv может интерпретировать как свои:

    ```bash
    uv run -- python -c "import sys; print(sys.path)"
    ```

### `uv run` vs `uvx` для проектных инструментов

Помимо `uv run` в `uv` есть команда `uvx` (подробнее - в [разделе про uvx](#uvx---запуск-инструментов-без-установки)),
которая запускает CLI-утилиты в изолированном временном окружении.
Может возникнуть вопрос: зачем писать `uv run pytest`, если есть `uvx pytest`?

`uvx pytest` технически запустится, но выполнит pytest в изолированном
временном окружении, не имеющем доступа к коду проекта и его зависимостям.
Тесты упадут с `ModuleNotFoundError` при первом же импорте модуля проекта.

Правило: инструменты, которые импортируют код проекта (`pytest`, `mypy`,
`coverage`, `alembic`), всегда запускаются через `uv run`. Самодостаточные
инструменты, которые только читают файлы (`ruff`, `black`, `isort`), могут
работать и через `uvx`, но если они добавлены в dev-зависимости -
последовательнее использовать `uv run`.

## Автономные скрипты с inline-зависимостями (PEP 723)

### Что такое PEP 723

[PEP 723](https://peps.python.org/pep-0723/) определяет стандартный формат для указания
метаданных (включая зависимости) непосредственно в Python-скрипте.
Это позволяет создавать полностью автономные скрипты - для их запуска
достаточно одного `.py` файла и `uv`.

### Формат метаданных

Метаданные размещаются в специальном блоке комментариев в начале скрипта:

```python
# /// script
# requires-python = ">=3.12"
# dependencies = [
#     "requests",
#     "rich",
# ]
# ///

import requests
from rich import print

response = requests.get("https://httpbin.org/json")
data = response.json()
print(data)
```

Формат блока:

- Открывающий маркер: `# /// script`
- Содержимое: TOML-синтаксис, каждая строка начинается с `#`
- Закрывающий маркер: `# ///`

### Запуск скрипта с inline-зависимостями

```bash
# uv читает зависимости из скрипта и устанавливает их автоматически
uv run fetch_data.py
```

При запуске uv:

1. Читает блок `# /// script` из файла.
2. Создает временное изолированное окружение.
3. Устанавливает указанные зависимости.
4. Выполняет скрипт.

Временное окружение кешируется, поэтому повторные запуски того же скрипта с теми
же зависимостями выполняются быстро.

### Управление зависимостями скрипта

`uv` предоставляет команды для редактирования метаданных скрипта:

```bash
# Добавить зависимость в метаданные скрипта
uv add --script fetch_data.py httpx

# Удалить зависимость из метаданных скрипта
uv remove --script fetch_data.py requests

# Инициализация метаданных скрипта в существующем файле
uv init --script utils.py --python ">=3.12"
```

После `uv add --script` блок метаданных в файле обновляется автоматически.

### Shebang для прямого запуска

Если добавить shebang в начало скрипта, его можно запускать напрямую, без `uv run`:

```python
#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.12"
# dependencies = ["httpx"]
# ///

import httpx
print(httpx.get("https://example.com").status_code)
```

```bash
chmod +x fetch.py
./fetch.py
```

Флаг `-S` в shebang необходим: без него ядро Linux воспринимает `uv run --script`
как одно имя программы. `-S` указывает `env` разбить строку на отдельные аргументы.
Поддерживается в GNU coreutils >= 8.30 (2018+) и macOS.

### Фиксация версий зависимостей скрипта

Для критичных скриптов можно создать lock-файл,
фиксирующий точные версии зависимостей:

```bash
# Создать lock-файл рядом со скриптом
uv lock --script deploy.py
# Результат: deploy.py.lock
```

После этого `uv run deploy.py` будет использовать зафиксированные версии.
Файл `*.py.lock` рекомендуется коммитить в git вместе со скриптом.

### Полный пример: утилита для проверки API

```python
# /// script
# requires-python = ">=3.12"
# dependencies = [
#     "httpx",
#     "rich",
# ]
# ///

"""Utility to check API endpoint health."""

import sys
import httpx
from rich.console import Console
from rich.table import Table

ENDPOINTS = [
    "https://httpbin.org/status/200",
    "https://httpbin.org/status/404",
    "https://httpbin.org/delay/1",
]

def main():
    console = Console()
    table = Table(title="API Health Check")
    table.add_column("Endpoint", style="cyan")
    table.add_column("Status", style="bold")
    table.add_column("Time (ms)", justify="right")

    for url in ENDPOINTS:
        try:
            response = httpx.get(url, timeout=5.0)
            status = f"[green]{response.status_code}[/]" if response.status_code < 400 \
                else f"[red]{response.status_code}[/]"
            elapsed = f"{response.elapsed.total_seconds() * 1000:.0f}"
        except httpx.RequestError as exc:
            status = f"[red]ERROR[/]"
            elapsed = "-"

        table.add_row(url, status, elapsed)

    console.print(table)

if __name__ == "__main__":
    main()
```

Запуск:

```bash
uv run api_check.py
```

### Безопасность inline-скриптов

Inline-скрипты позволяют выполнять чужой код вместе с
его зависимостями. При запуске непроверенного скрипта
учитывайте риски:

- **Typosquatting** - пакет с похожим именем (`reqeusts` вместо `requests`)
  может содержать вредоносный код. Перед запуском проверяйте имена
  пакетов в блоке `dependencies`.
- Зависимости устанавливаются в изолированное окружение,
  но код скрипта выполняется с правами текущего пользователя.

!!! warning "Проверяйте зависимости"
    Не запускайте через `uv run` скрипты из непроверенных источников.
    Всегда просматривайте список зависимостей в блоке `# /// script`
    перед первым запуском.

### Когда использовать inline-зависимости

| Сценарий | Подход |
| -------- | ------ |
| Утилитарный скрипт для команды | Inline-зависимости (один файл, легко передать) |
| Одноразовая задача (парсинг, миграция данных) | Inline-зависимости |
| Полноценный проект с несколькими модулями | `pyproject.toml` + `uv.lock` |
| Скрипт, который нужно версионировать с точными версиями | `pyproject.toml` + `uv.lock` |

!!! tip "Удобно для обмена скриптами"
    Коллега может запустить ваш скрипт одной командой `uv run script.py` - ему
    не нужно вручную создавать окружение и устанавливать зависимости. Все
    описано прямо в файле.

## uvx - запуск инструментов без установки

`uvx` - это сокращение для `uv tool run`. Эта команда позволяет запускать
CLI-инструменты Python без предварительной установки. По функциональности
это аналог `pipx run`.

### Как работает uvx

При вызове `uvx <tool>`:

1. Создается временное изолированное окружение.
2. Указанный пакет устанавливается в это окружение.
3. Запускается точка входа (CLI-команда) пакета.
4. Окружение кешируется для повторных вызовов.

### Базовые примеры

```bash
# Запуск линтера ruff без установки в проект
uvx ruff check .

# Форматирование кода с помощью black
uvx black .

# Запуск сканера безопасности кода
uvx bandit -r src/

# Проверка сложности кода
uvx radon cc src/ -a

# Запуск Jupyter notebook
uvx jupyter notebook
```

### Указание версии и пакета

```bash
# Запуск конкретной версии
uvx --from "ruff==0.15.0" ruff check .

# Когда имя команды отличается от имени пакета
uvx --from httpie http GET https://httpbin.org/json

# Запуск с конкретной версией Python
uvx --python 3.12 jupyter notebook
```

Флаг `--from` необходим в двух случаях:

- Когда нужна конкретная версия пакета.
- Когда имя CLI-команды отличается от имени пакета
  (например, пакет `httpie` предоставляет команду `http`).

### Версионирование, кеш и плагины

Версию пакета можно указать через `@`:

```bash
# Конкретная версия
uvx ruff@0.15.0 check .

# Принудительно последняя версия (обновляет кеш)
uvx ruff@latest check .
```

После первого вызова `uvx ruff` версия кешируется.
Последующие вызовы используют ту же версию, даже если
вышла новая. Чтобы обновить - используйте `@latest`.

Если инструменту нужны плагины, их можно добавить
через `--with`:

```bash
# mkdocs с плагином для темы
uvx mkdocs --with mkdocs-material build

# pytest с плагином для async
uvx --with pytest-asyncio pytest
```

Плагины устанавливаются в то же временное окружение,
что и основной инструмент.

### Типичные инструменты для uvx

| Инструмент | Команда | Назначение |
| ---------- | ------- | ---------- |
| ruff | `uvx ruff check .` | Линтер и форматтер |
| black | `uvx black .` | Форматирование кода |
| isort | `uvx isort .` | Сортировка импортов |
| mypy | `uvx mypy src/` | Проверка типов |
| bandit | `uvx bandit -r src/` | Проверка безопасности |
| pre-commit | `uvx pre-commit run --all-files` | Git-хуки |
| cookiecutter | `uvx cookiecutter gh:user/template` | Генерация проекта из шаблона |
| jupyter | `uvx jupyter notebook` | Интерактивные ноутбуки |

!!! note "uvx vs установка в проект"
    `uvx` предназначен для инструментов командной строки, а не для библиотек.
    Если инструмент нужен как зависимость проекта (например, pytest в
    dev-группе), добавьте его через `uv add --dev pytest`. `uvx` подходит для
    разовых проверок или инструментов, которые не привязаны к конкретному
    проекту.

## uv tool install - постоянная установка инструментов

Если вы часто используете какой-то CLI-инструмент, его можно установить
глобально через `uv tool install`. В отличие от `uvx`, установленные инструменты
доступны из любого каталога без дополнительных задержек.

### Установка и управление

```bash
# Глобальная установка инструмента
uv tool install ruff

# Установка с конкретной версией Python
uv tool install --python 3.12 jupyter

# Установка конкретной версии
uv tool install "ruff>=0.15.0"
```

### Просмотр и удаление

```bash
# Список всех установленных инструментов
uv tool list

# Обновление инструмента до последней версии
uv tool upgrade ruff

# Обновление всех установленных инструментов
uv tool upgrade --all

# Удаление инструмента
uv tool uninstall ruff
```

### Настройка PATH

Инструменты устанавливаются на уровне пользователя, а не проекта. Исполняемые
файлы размещаются в `~/.local/bin/` (Linux / WSL 2 / macOS). Чтобы обновить PATH:

```bash
# Убедитесь, что исполняемые файлы инструментов в PATH
uv tool update-shell
```

Эта команда добавляет `~/.local/bin/` в конфигурацию вашего shell, если это еще
не сделано.

### Где хранятся инструменты

```bash
# Показать директорию хранения окружений инструментов
uv tool dir
# ~/.local/share/uv/tools/ (Linux)
```

Каждый инструмент устанавливается в свое изолированное окружение. Это означает,
что зависимости разных инструментов не конфликтуют друг с другом.

### uvx vs uv tool install - сравнение

| Характеристика | `uvx` (uv tool run) | `uv tool install` |
| -------------- | ------------------- | ----------------- |
| Установка | Временная (кешируется) | Постоянная |
| Доступность | При вызове через `uvx` | Из любого каталога напрямую |
| Обновление | Автоматически при первом вызове | Вручную: `uv tool upgrade` |
| Удаление | Кеш очищается автоматически | `uv tool uninstall` |
| Подходит для | Разовые проверки, редкие инструменты | Часто используемые инструменты |

!!! tip "Рекомендуемый подход"
    Установите через `uv tool install` инструменты, которые вы используете
    ежедневно (ruff, mypy, pre-commit). Для всего остального достаточно `uvx`.

## Переменные окружения и файлы .env

При разработке приложений часто требуется передавать конфигурацию через
переменные окружения: токены API, строки подключения к базам данных, режимы
работы. Команда `uv run` поддерживает загрузку переменных из `.env` файлов.

### Загрузка из .env файла

```bash
# Загрузка переменных из .env перед запуском
uv run --env-file .env python app.py
```

Формат `.env` файла:

```bash
# .env
DATABASE_URL=postgresql://user:pass@localhost:5432/mydb
API_KEY=sk-example-key-12345
DEBUG=true
```

### Несколько .env файлов

Можно указать несколько файлов. Значения из последующих файлов перезаписывают
значения из предыдущих:

```bash
# Загрузка базового конфига, затем перезапись локальными настройками
uv run --env-file .env --env-file .env.local python app.py
```

Это удобно для разделения базовой конфигурации и локальных настроек:

```bash
# .env - базовый конфиг (коммитится в git)
APP_NAME=my-service
LOG_LEVEL=info

# .env.local - локальные переопределения (в .gitignore)
DATABASE_URL=postgresql://localhost:5432/dev
API_KEY=sk-dev-key
DEBUG=true
```

### Настройка через переменные окружения uv

Вместо флага `--env-file` можно использовать переменные окружения:

```bash
# Задать файл .env по умолчанию
export UV_ENV_FILE=.env

# Теперь uv run всегда загружает .env
uv run python app.py

# Полностью отключить загрузку .env
export UV_NO_ENV_FILE=1
```

### Приоритет значений

Переменные окружения из разных источников имеют следующий приоритет (от высшего
к низшему):

1. **Реальные переменные окружения** - установленные в shell (`export VAR=value`).
2. **Более поздние .env файлы** - правый `--env-file` перезаписывает левый.
3. **Более ранние .env файлы** - базовые значения.

```bash
# Переменная оболочки имеет приоритет над .env
export DEBUG=false
uv run --env-file .env python -c "import os; print(os.environ['DEBUG'])"
# Вывод: false (даже если в .env стоит DEBUG=true)
```

### Пример: приложение с конфигурацией

```python
"""Simple app that reads configuration from environment variables."""

import os

def main():
    db_url = os.environ.get("DATABASE_URL", "sqlite:///local.db")
    debug = os.environ.get("DEBUG", "false").lower() == "true"
    api_key = os.environ.get("API_KEY")

    print(f"Database: {db_url}")
    print(f"Debug mode: {debug}")
    print(f"API key configured: {api_key is not None}")

if __name__ == "__main__":
    main()
```

Запуск:

```bash
uv run --env-file .env python config_demo.py
```

    Файлы с секретами (`.env.local`, `.env.production`) должны быть в
    `.gitignore`. Коммитить можно только шаблон (`.env.example`) с
    пустыми значениями:

    ```bash
    # .env.example (коммитится в git)
    DATABASE_URL=
    API_KEY=
    DEBUG=false
    ```
