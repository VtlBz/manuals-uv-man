# Раздел 3. Управление версиями Python

---

## Концепция: managed vs system Python

uv делит все установленные интерпретаторы Python на две категории:

**Managed Python** - версии, установленные самим uv. Они хранятся в специальной
директории (по умолчанию `~/.local/share/uv/python/` на Linux/macOS). Управление
ими целиком лежит на uv: установка, обновление, удаление.

**System Python** - все остальные интерпретаторы: установленные операционной
системой, собранные вручную, или установленные через другие менеджеры
(pyenv, Homebrew, deadsnakes PPA и т.д.).

!!! warning "Важно для пользователей pyenv"
    uv считает Python, установленный через pyenv, **системным** (system). Для uv
    нет разницы между `/usr/bin/python3` и `~/.pyenv/versions/3.12.0/bin/python`
    - оба являются "system Python".

Это фундаментальное отличие от pyenv, где установленные версии являются
"управляемыми" самим pyenv. В мире uv "managed" означает только одно -
установлен через `uv python install`.

### Где хранятся managed Python

| Параметр | Значение |
| --- | --- |
| Директория по умолчанию (Linux/macOS) | `~/.local/share/uv/python/` |
| Директория по умолчанию (Windows) | `%APPDATA%\uv\data\python\` |
| Переменная для переопределения | `UV_PYTHON_INSTALL_DIR` |
| Команда для просмотра пути | `uv python dir` |

Для сравнения: pyenv хранит свои версии в `~/.pyenv/versions/`.

```bash
# Где uv хранит managed Python
uv python dir

# Где pyenv хранит Python
pyenv root
```

## Стратегии управления Python в команде

При внедрении `uv` в команде необходимо выбрать стратегию
работы с версиями Python. Ниже описаны три основных подхода.

!!! note "Авторская классификация"
    Названия стратегий (A, B, C) - условная классификация
    на основе реальных настроек `uv`, а не официальная
    терминология проекта.

### Стратегия A: только managed Python

`uv` полностью отвечает за установку Python. Системные
интерпретаторы и сторонние менеджеры не используются.

```toml
# ~/.config/uv/uv.toml
python-preference = "only-managed"
python-downloads = "automatic"
```

**Достоинства:**

- Единственный инструмент - минимальная сложность.
- Zero-setup: на новой машине достаточно установить `uv`
  и выполнить `uv sync` - Python скачивается автоматически.
- В Docker и CI не нужен отдельный шаг установки Python.
- Не требуются системные build-зависимости.

**Недостатки:**

- Python из python-build-standalone имеет ряд особенностей
  (см. раздел «Особенности standalone Python» ниже).
- Без `uv run` или активации виртуального окружения
  команда `python` может быть недоступна в терминале.

**Когда выбирать:**

- Новая команда без инфраструктурных ограничений.
- Проекты без специфических требований (Nuitka,
  tkinter, сложные C-расширения).
- Важна простота онбординга новых участников.

### Стратегия B: только системный Python

`uv` используется как замена `pip` + `venv` + `pip-tools`.
Версии Python устанавливаются отдельно (`pyenv`, пакетный
менеджер ОС и т.д.).

```toml
# ~/.config/uv/uv.toml
python-preference = "only-system"
python-downloads = "never"
```

**Достоинства:**

- Нет дополнительного источника Python в системе.
- Отсутствуют особенности python-build-standalone.
- Экономия дискового пространства.

**Недостатки:**

- Теряется автоматическое обеспечение нужной версии
  Python на новой машине.
- В Docker и CI требуется отдельный шаг установки.

**Когда выбирать:**

- Много legacy-проектов на `pyenv`.
- Жесткие политики безопасности в отношении
  источников бинарных файлов.
- Сложные сборки с нативным кодом.

### Стратегия C: гибридный подход

Системный Python (включая `pyenv`) используется
в приоритете, но `uv` может автоматически скачать
managed-версию, если нужная не найдена.

```toml
# ~/.config/uv/uv.toml
python-preference = "system"
python-downloads = "automatic"
```

**Достоинства:**

- Мягкая миграция - существующие привычки
  не нарушаются.
- Если проекту нужна версия, отсутствующая
  в системе, `uv` скачает ее автоматически.
- Позволяет оценить managed Python на практике.

**Недостатки:**

- Два источника Python может усложнить диагностику.
- Промежуточное состояние, в котором легко
  задержаться.

**Когда выбирать:**

- Переход с `pyenv` на `uv`.
- Переходный период (2-4 недели), после которого
  принимается решение в пользу стратегии A или B.

### Рекомендации по выбору стратегии

| Ситуация | Рекомендация |
| --- | --- |
| Новая команда без ограничений | Стратегия A |
| Переход с `pyenv` | Стратегия C, затем A |
| Жесткие требования безопасности | Стратегия B |
| Сложные нативные сборки | Стратегия B |

## Команды uv python

### Установка версий Python

```bash
# Установка минорной версии (последний патч)
uv python install 3.12

# Установка точной версии с патчем
uv python install 3.12.3

# Установка нескольких версий сразу
uv python install 3.11 3.12 3.13

# Установка с ограничением версии
uv python install '>=3.11,<3.13'
```

!!! tip "Автоматическая установка"
    В большинстве случаев вам не нужно вызывать `uv python install` явно. По
    умолчанию uv автоматически скачивает нужную версию Python, если она не
    найдена в системе. Подробнее об этом - в разделе
    "Автоматическая загрузка Python" (см. раздел ниже).

После установки uv также создает исполняемые файлы (например, `python3.12`) в
директории `~/.local/bin/`. Убедитесь, что эта директория есть в вашем `PATH`:

```bash
# Добавьте ~/.local/bin в PATH, если ещё не добавлено
uv python update-shell
```

### Просмотр доступных версий

```bash
# Список всех доступных и установленных версий Python
uv python list

# Показать только установленные версии
uv python list --only-installed

# Фильтр по минорной версии
uv python list 3.12

# Показать все патч-версии (включая старые)
uv python list --all-versions

# Показать версии для всех платформ
uv python list --all-platforms
```

Пример вывода `uv python list --only-installed`:

```text
cpython-3.13.2-linux-x86_64-gnu    ~/.local/share/uv/python/cpython-3.13.2-linux-x86_64-gnu/bin/python3
cpython-3.12.9-linux-x86_64-gnu    ~/.local/share/uv/python/cpython-3.12.9-linux-x86_64-gnu/bin/python3
cpython-3.11.11-linux-x86_64-gnu   /usr/bin/python3.11
```

!!! note "Обозначения в выводе"
    В выводе `uv python list` managed-версии показывают путь внутри
    `~/.local/share/uv/python/`, а system-версии - путь к системному
    интерпретатору (например,
    `/usr/bin/python3.11` или `~/.pyenv/versions/...`).

### Поиск конкретной версии

```bash
# Найти путь к конкретной версии Python
uv python find 3.12

# Найти только системный Python (пропустить виртуальные окружения)
uv python find --system 3.12

# Найти Python по ограничению версии
uv python find '>=3.11'
```

Команда `uv python find` возвращает полный путь к исполняемому файлу Python,
что полезно для отладки и скриптов.

### Закрепление версии для проекта

```bash
# Фиксация версии Python для текущего проекта (создает .python-version)
uv python pin 3.12

# Фиксация глобально (пользовательский уровень)
uv python pin --global 3.12
```

### Удаление managed-версий

```bash
# Удаление managed-версии Python
uv python uninstall 3.11

# Удаление нескольких версий
uv python uninstall 3.10 3.11
```

!!! warning "Ограничение"
    Команда `uv python uninstall` удаляет только managed-версии Python.
    Системные интерпретаторы она не затрагивает.

### Обновление managed-версий

```bash
# Обновление до последнего патча 3.12
uv python upgrade 3.12

# Обновление всех установленных managed-версий
uv python upgrade
```

!!! note "Только патч-обновления"
    Команда `uv python upgrade` обновляет только в пределах минорной версии
    (например, 3.12.3 -> 3.12.5), но не переключает на следующую минорную версию
    (3.12 -> 3.13), так как это может повлиять на разрешение зависимостей.

## Как uv ищет Python

Когда `uv` требуется интерпретатор (создание виртуального
окружения, запуск скрипта и т.п.), поиск выполняется
в определенном порядке.

**Определение требуемой версии:**

1. Флаг `--python` командной строки (высший приоритет).
2. Файл `.python-version` в текущей или родительской
   директории.
3. Поле `requires-python` в `pyproject.toml`.
4. Если ничего не указано - первая доступная версия.

**Источники интерпретаторов (где `uv` ищет):**

1. Активное виртуальное окружение (`$VIRTUAL_ENV`).
2. Директория `.venv` в текущем каталоге.
3. Managed Python (`~/.local/share/uv/python/`).
4. System Python (все интерпретаторы в `PATH`).

Порядок пунктов 3 и 4 регулируется параметром
`python-preference`
(см. раздел «Настройка python-preference» ниже).

!!! tip "Отладка выбора Python"
    Команда `uv python find` показывает, какой именно
    интерпретатор будет выбран в текущем каталоге
    с учетом всех настроек.

## Файл .python-version

Файл `.python-version` - это простой текстовый файл, содержащий версию Python
для проекта. Этот формат является стандартом де-факто и
поддерживается как uv, так и pyenv.

### Кто читает .python-version

Не все инструменты экосистемы Python используют
этот файл:

| Инструмент | Читает `.python-version` |
| --- | --- |
| `uv` | Да, при любой операции с Python |
| `pyenv` | Да, переключает shims на указанную версию |
| `pip` | Нет |
| IDE (PyCharm, VS Code) | Зависит от настроек; поддержка неполная |

### Создание и содержимое

```bash
# Создание .python-version в текущей директории
uv python pin 3.12
```

После выполнения в текущей директории появится
файл `.python-version` с содержимым:

```text
3.12
```

### Порядок поиска

uv ищет файл `.python-version` в следующем порядке:

1. Текущая директория.
2. Родительские директории (вверх по дереву до корня проекта/workspace).
3. Пользовательская конфигурация (`~/.config/uv/` на Linux/macOS).

!!! note "Границы поиска"
    uv не ищет `.python-version` за пределами проекта или workspace. Если файл
    не найден ни в проекте, ни в пользовательской конфигурации, uv использует
    алгоритм обнаружения Python по умолчанию.

### Совместимость с pyenv

Файл `.python-version` - это тот самый файл, который использует pyenv при вызове
`pyenv local`. Это дает важное преимущество: один и тот же
файл работает с обоими инструментами.

```bash
# Обе команды создают одинаковый файл .python-version
pyenv local 3.12      # pyenv way
uv python pin 3.12    # uv way
```

!!! tip "Рекомендация по формату"
    Записывайте в `.python-version` только номер версии (например, `3.12`), без
    указания реализации или платформы. Это обеспечивает максимальную
    совместимость между uv, pyenv и другими инструментами.

    Допустимые форматы: `3.12`, `3.12.3`, `3` (но
    последний вариант слишком общий).

## Настройка python-preference

Параметр `python-preference` контролирует, какой Python uv предпочитает
использовать - managed (установленный самим uv) или system (все остальные).

### Возможные значения

| Значение | Поведение | Эквивалент флага |
| --- | --- | --- |
| `managed` (по умолчанию) | Предпочитает managed Python, при отсутствии использует system | - |
| `system` | Предпочитает system Python над managed | - |
| `only-managed` | Использует **только** managed Python, system игнорируется | `--managed-python` |
| `only-system` | Использует **только** system Python, managed игнорируется | `--no-managed-python` |

### Подробное описание каждого режима

=== "managed (по умолчанию)"

    Режим по умолчанию. uv сначала ищет подходящий managed Python. Если
    managed-версия не найдена, использует system Python. Если ни один Python не
    найден - автоматически скачивает managed-версию (при
    включенных автоматических загрузках).

    ```toml
    # pyproject.toml
    [tool.uv]
    python-preference = "managed"
    ```

    Это оптимальный выбор для большинства проектов: uv контролирует версию
    Python, обеспечивая воспроизводимость сборки.

=== "system"

    uv сначала ищет system Python (включая pyenv-установленный). Managed-версии
    используются только как fallback.

    ```toml
    # pyproject.toml
    [tool.uv]
    python-preference = "system"
    ```

    Полезно при переходе с pyenv: вы продолжаете использовать
    pyenv-установленные версии, но можете постепенно переходить на managed.

=== "only-managed"

    uv работает **исключительно** с managed Python. Системные интерпретаторы
    полностью игнорируются, даже если они есть в `PATH`.

    ```toml
    # pyproject.toml
    [tool.uv]
    python-preference = "only-managed"
    ```

    Эквивалент флага `--managed-python` для каждой команды. Гарантирует полную
    изоляцию от системного окружения.

=== "only-system"

    uv работает **исключительно** с system Python. Managed-версии не
    используются, автоматическая загрузка отключена.

    ```toml
    # pyproject.toml
    [tool.uv]
    python-preference = "only-system"
    ```

    Эквивалент флага `--no-managed-python`. Подходит для окружений, где Python
    установлен через системный менеджер пакетов и вы хотите использовать именно
    его (например, в Docker-контейнерах с предустановленным Python).

### Где задавать python-preference

Параметр можно задать несколькими способами (в
порядке приоритета, от высшего к низшему):

```bash
# 1. Флаг командной строки (высший приоритет)
uv venv --python-preference system

# 2. Переменная окружения
export UV_PYTHON_PREFERENCE=system

# 3. Конфиг проекта в pyproject.toml
# [tool.uv]
# python-preference = "system"

# 4. Конфиг проекта в uv.toml
# python-preference = "system"

# 5. Пользовательский конфиг в ~/.config/uv/uv.toml (низший приоритет)
# python-preference = "system"
```

=== "pyproject.toml"

    ```toml
    [tool.uv]
    python-preference = "managed"
    ```

=== "uv.toml"

    ```toml
    python-preference = "managed"
    ```

=== "Переменная окружения"

    ```bash
    export UV_PYTHON_PREFERENCE="managed"
    ```

## Автоматическая загрузка Python

По умолчанию, если uv не находит подходящую версию Python, он автоматически
скачивает и устанавливает managed-версию. Это одна из ключевых особенностей uv,
обеспечивающая принцип "just works".

### Управление автоматической загрузкой

Параметр `python-downloads` контролирует это поведение:

| Значение | Поведение |
| --- | --- |
| `automatic` (по умолчанию) | Python скачивается автоматически при необходимости |
| `manual` | Скачивание только через явный вызов `uv python install` |

=== "pyproject.toml"

    ```toml
    [tool.uv]
    python-downloads = "manual"
    ```

=== "uv.toml"

    ```toml
    python-downloads = "manual"
    ```

=== "Переменная окружения"

    ```bash
    export UV_PYTHON_DOWNLOADS=manual
    ```

=== "Флаг командной строки"

    ```bash
    uv sync --no-python-downloads
    ```

!!! tip "Когда отключать автоматическую загрузку"
    Отключение полезно в контролируемых окружениях:

    - Docker: Python уже установлен в базовом образе, скачивание не нужно.
    - **CI/CD**: Python предустановлен в раннере,
      загрузка добавляет лишнее время.
    - **Корпоративные сети**: ограниченный доступ к интернету.

    Пример для Docker:

    ```dockerfile
    FROM python:3.12-slim
    COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
    ENV UV_PYTHON_DOWNLOADS=manual
    ENV UV_PYTHON_PREFERENCE=only-system
    ```

### Значение never

Помимо `automatic` и `manual`, параметр `python-downloads`
поддерживает значение `never` - полный запрет на скачивание
managed Python:

| Значение | `uv python install` | Автозагрузка |
| --- | --- | --- |
| `automatic` | Работает | Да |
| `manual` | Работает | Нет |
| `never` | Ошибка | Нет |

Значение `never` отличается от `manual` тем, что запрещает
скачивание даже через явную команду `uv python install`.

### Комбинации настроек для типовых стратегий

Сочетание `python-preference` и `python-downloads` определяет
стратегию работы с Python. Готовые конфигурации для
`~/.config/uv/uv.toml`:

=== "Только managed Python (стратегия A)"

    ```toml
    python-preference = "only-managed"
    python-downloads = "automatic"
    ```

=== "Только системный Python (стратегия B)"

    ```toml
    python-preference = "only-system"
    python-downloads = "never"
    ```

=== "Гибридный подход (стратегия C)"

    ```toml
    python-preference = "system"
    python-downloads = "automatic"
    ```

## Особенности standalone Python

Managed-версии Python, устанавливаемые через `uv`,
представляют собой сборки из проекта
python-build-standalone. Эти сборки имеют ряд отличий
от Python, установленного через пакетный менеджер ОС
или собранного из исходников.

!!! warning "Специфика python-build-standalone"
    Перечисленные ниже особенности относятся
    исключительно к дистрибутивам
    python-build-standalone, которые `uv` использует
    для managed Python. Системный Python (установленный
    через `apt`, `brew`, `pyenv` и т.д.) этим
    особенностям не подвержен.

### Статически слинкованный OpenSSL

В стандартном Linux-Python библиотека OpenSSL загружается
из системы динамически и обновляется вместе с ОС.
В managed Python OpenSSL вкомпилирован статически.
Для получения обновлений безопасности необходимо
переустанавливать managed Python:

```bash
# Переустановка для обновления OpenSSL
uv python install --reinstall 3.12
```

В Docker-окружениях это означает пересборку образов
без кэша.

### Проблемы с terminfo в REPL

При прямом запуске managed Python (без `uv run`)
в интерактивном режиме (REPL) могут не работать клавиши
стрелок и Backspace. Причина - отсутствие привязки
к системной базе terminfo.

Запуск через `uv run python` обычно не вызывает
этой проблемы.

### Пути sysconfig

Сборки python-build-standalone содержат абсолютные пути
сборочной машины в конфигурации sysconfig. Большинство
инструментов корректно обрабатывают эту ситуацию, однако
утилиты упаковки в standalone-бинарь (Nuitka, cx_Freeze)
могут работать некорректно.

### Ограничения стандартной библиотеки

Некоторые модули стандартной библиотеки могут быть
недоступны или работать с ограничениями. Исторически
это касалось `tkinter` и ряда криптографических функций.
Для типового веб-, CLI- или data-кода эти ограничения
не проявляются.

## Сосуществование с pyenv

Это один из самых важных разделов для тех, кто переходит с pyenv на uv. Оба
инструмента могут работать на одной системе, но
есть нюансы, о которых нужно знать.

### Как uv обнаруживает pyenv-установленный Python

uv обнаруживает Python-интерпретаторы через стандартный механизм
поиска в `PATH`. Для pyenv это означает:

1. Если pyenv настроен через shims (`~/.pyenv/shims/` в `PATH`),
   uv находит Python через эти shims.
2. Если pyenv не использует shims (например, при использовании `pyenv shell` с
   прямым путем), uv найдет Python по полному пути в `PATH`.
3. uv также может найти pyenv-версии напрямую, если
   указать полный путь к интерпретатору.

### Проблема: shims pyenv

Pyenv использует механизм shims - легковесных скриптов-оберток в
`~/.pyenv/shims/`, которые перенаправляют вызовы к реальному интерпретатору. Это
может вызывать проблемы при работе с uv.

!!! warning "Типичная ошибка"
    Если pyenv shim для запрашиваемой версии
    существует, но сама версия не установлена:

    ```text
    pyenv: python3.12: command not found

    The 'python3.12' command exists in these Python versions:
      3.12.0
      3.12.3

    Note: See 'pyenv help global' for tips on allowing both
          python2 and python3 to be found.
    ```

    uv вызывает shim `python3.12`, shim обращается к pyenv, но pyenv не находит
    установленную версию. В результате uv получает ошибку вместо интерпретатора.

### Решения проблемы shims

#### Решение 1: Активировать все нужные версии через pyenv global

```bash
# Сделать все установленные версии доступными через shims
pyenv global 3.11.11 3.12.9 3.13.2

# Проверка: все версии должны быть доступны
python3.11 --version
python3.12 --version
python3.13 --version
```

Когда несколько версий указаны в `pyenv global`, shims для `python3.11`,
`python3.12`, `python3.13` корректно перенаправляют на
соответствующие установленные версии.

#### Решение 2: Использовать переменную PYENV_VERSION

```bash
# Задать версию для одной команды uv
PYENV_VERSION=3.12.9 uv venv

# Или экспортировать на сессию
export PYENV_VERSION=3.12.9
uv sync
```

#### Решение 3: Указать полный путь к интерпретатору

```bash
# Использовать полный путь, минуя shims
uv venv --python ~/.pyenv/versions/3.12.9/bin/python

# Или для uv run
uv run --python ~/.pyenv/versions/3.12.9/bin/python script.py
```

#### Решение 4: Использовать python-preference = "managed"

```bash
# Пропустить системный/pyenv Python, использовать только managed-версии
uv venv --python-preference managed --python 3.12
```

Это наиболее чистое решение: uv использует собственные managed-версии
и не зависит от shims pyenv вообще.

### Конфликт .python-version с pyenv-virtualenv

Плагин **pyenv-virtualenv** записывает в файл `.python-version` не номер
версии, а имя виртуального окружения:

```text
# .python-version, созданный pyenv-virtualenv
my-project-env
```

Это не является валидным номером версии Python, и uv не может использовать такое
значение для выбора интерпретатора.

!!! info "Поведение uv (начиная с v0.6+)"
    Начиная с версии 0.6, uv **игнорирует** записи в `.python-version`, которые
    не являются валидными спецификациями версий Python. Если uv встретит имя
    pyenv-virtualenv (например, `my-project-env`), он просто пропустит этот файл
    и продолжит поиск подходящего интерпретатора по стандартному алгоритму.

    В более ранних версиях uv это приводило к ошибке. Если вы используете
    старую версию uv - обновите его.

### Стратегия перехода с pyenv на uv

Переход не обязан быть мгновенным. Рекомендуемый поэтапный план:

#### Этап 1: Параллельное использование

На этом этапе pyenv остается основным менеджером версий Python, а uv
используется для управления зависимостями и виртуальными окружениями.

```toml
# pyproject.toml - использование Python из pyenv
[tool.uv]
python-preference = "system"
```

```bash
# pyenv по-прежнему управляет версиями Python
pyenv install 3.12.9
pyenv local 3.12

# uv использует версию, установленную через pyenv
uv sync
```

#### Этап 2: Установка Python через uv

Начните устанавливать новые версии через uv,
сохраняя pyenv для уже установленных.

```bash
# Установка новой версии через uv
uv python install 3.13

# Сохранение существующих версий pyenv
pyenv versions  # 3.11.11, 3.12.9 - still here

# Переключение на предпочтение по умолчанию (managed первым)
# pyproject.toml:
# [tool.uv]
# python-preference = "managed"
```

#### Этап 3: Полный переход

Когда все проекты переведены на uv-managed Python, pyenv можно удалить.

```bash
# Установка всех нужных версий через uv
uv python install 3.11 3.12 3.13

# Проверка установок
uv python list --only-installed

# Фиксация версии для каждого проекта
cd my-project
uv python pin 3.12

# Удаление pyenv (опционально, когда готовы)
# pyenv versions  -> больше не нужен
# rm -rf ~/.pyenv  -> финальная очистка
```

### Пошаговая миграция

Если принято решение полностью отказаться от `pyenv`,
рекомендуется трехшаговая процедура: отключить -
проверить - удалить.

#### Шаг 1. Отключение (без удаления)

В shell-конфигах необходимо найти и **закомментировать**
(не удалять) строки инициализации `pyenv`:

```bash
# Поиск файлов с инициализацией pyenv
grep -l "pyenv" ~/.bashrc ~/.bash_profile ~/.profile \
                ~/.zshrc ~/.zprofile ~/.zshenv 2>/dev/null
```

Типичные строки для комментирования:

```bash
# export PYENV_ROOT="$HOME/.pyenv"
# [[ -d $PYENV_ROOT/bin ]] && export PATH="$PYENV_ROOT/bin:$PATH"
# eval "$(pyenv init - bash)"
# eval "$(pyenv virtualenv-init -)"
```

После перезапуска терминала - проверка:

```bash
# Команда pyenv не должна находиться
command -v pyenv
# Ожидаемый результат: пусто, exit code 1

# В PATH не должно быть pyenv
echo "$PATH" | tr ':' '\n' | grep -i pyenv
# Ожидаемый результат: пусто
```

#### Шаг 2. Проверка (1-2 недели)

В течение 1-2 недель работы без `pyenv` убедиться:

- Все проекты собираются и запускаются через `uv`.
- CI остается зеленым.
- Docker-образы собираются без ошибок.
- Не обнаружены хардкод-пути вида
  `~/.pyenv/versions/3.x.y/bin/python` в Makefile,
  скриптах, конфигурации IDE, pre-commit хуках.

!!! tip "Откат"
    Если что-то сломалось - достаточно раскомментировать
    строки из шага 1. Каталог `~/.pyenv/` остается
    на месте.

#### Шаг 3. Полное удаление

После успешной проверки:

```bash
# Удалить закомментированные строки из shell-конфигов

# Удалить каталог pyenv
rm -rf ~/.pyenv

# Если pyenv был установлен через Homebrew
brew uninstall pyenv pyenv-virtualenv 2>/dev/null

# Проверить отсутствие системных конфигов
ls /etc/profile.d/ 2>/dev/null | grep -i pyenv
```

После удаления необходимо перезапустить все открытые
терминалы.

### Сравнение команд pyenv и uv

| Действие | pyenv | uv |
| --- | --- | --- |
| Установить версию | `pyenv install 3.12` | `uv python install 3.12` |
| Удалить версию | `pyenv uninstall 3.12.0` | `uv python uninstall 3.12` |
| Список установленных | `pyenv versions` | `uv python list --only-installed` |
| Список доступных | `pyenv install --list` | `uv python list` |
| Закрепить для проекта | `pyenv local 3.12` | `uv python pin 3.12` |
| Закрепить глобально | `pyenv global 3.12` | `uv python pin --global 3.12` |
| Найти путь к Python | `pyenv which python3.12` | `uv python find 3.12` |
| Обновить патч-версию | Переустановка: `pyenv install 3.12.5` | `uv python upgrade 3.12` |

!!! tip "Преимущество uv"
    В отличие от pyenv, uv не компилирует Python из исходников. Managed-версии -
    это предсобранные бинарные дистрибутивы (из проекта
    python-build-standalone), оптимизированные с PGO и LTO.
    Установка занимает секунды, а не минуты.

## requires-python в pyproject.toml

Помимо `.python-version`, существует еще один механизм указания версии Python -
поле `requires-python` в `pyproject.toml`.

### Назначение

```toml
[project]
name = "my-project"
requires-python = ">=3.11"
```

Поле `requires-python` определяет **диапазон совместимых
версий** Python для проекта. Это влияет на:

- Разрешение зависимостей (uv выбирает пакеты,
  совместимые с указанным диапазоном).
- Выбор интерпретатора: uv ищет первую совместимую версию.
- Сборку и публикацию: метаданные пакета содержат ограничение версии Python.

### Отличия от .python-version

| Характеристика | `.python-version` | `requires-python` |
| --- | --- | --- |
| Назначение | Запрос конкретной версии для работы | Диапазон совместимых версий |
| Формат | Точная версия: `3.12` | Спецификатор: `>=3.11`, `>=3.11,<3.14` |
| Область действия | Текущая директория (и ниже) | Весь проект |
| Влияет на зависимости | Нет | Да |
| Используется при сборке | Нет | Да |
| Совместимость | pyenv, uv, другие инструменты | pip, uv, poetry, стандарт PEP 621 |

### Как uv использует оба параметра

Когда существуют оба файла, uv действует по следующей логике:

1. Если указан `--python` флаг - используется он (высший приоритет).
2. Если есть `.python-version` - uv пытается найти/установить эту версию.
3. Найденная версия проверяется на соответствие `requires-python`.
4. Если версия из `.python-version` не соответствует
   `requires-python`, uv выдает ошибку.

!!! example "Пример конфликта"

    ```text
    # .python-version
    3.10
    ```

    ```toml
    # pyproject.toml
    [project]
    requires-python = ">=3.12"
    ```

    При запуске `uv sync` вы получите ошибку, потому что Python 3.10 не
    удовлетворяет требованию `>=3.12`. Решение - обновить
    `.python-version` до совместимой версии:

    ```bash
    uv python pin 3.12
    ```
