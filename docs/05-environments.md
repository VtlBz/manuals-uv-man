## Как uv управляет .venv автоматически

В классическом рабочем процессе с `pip` вы привыкли вручную создавать
виртуальное окружение, активировать его, а затем устанавливать зависимости.
С `uv` этот процесс упрощается до минимума.

При первом выполнении `uv sync` или `uv run` в каталоге проекта `uv` автоматически:

1. Определяет нужную версию Python (из `.python-version` или `requires-python` в
   `pyproject.toml`).
2. Создает директорию `.venv` в корне проекта.
3. Устанавливает все зависимости из lockfile.

```bash
# Инициализация нового проекта
uv init my-app
cd my-app

# .venv ещё не существует
ls -la .venv
# ls: cannot access '.venv': No such file or directory

# uv sync создает .venv автоматически
uv sync
# Using CPython 3.12.x
# Creating virtual environment at: .venv
# Resolved 1 package in 5ms
# Installed 1 package in 3ms

# .venv создан
ls .venv/bin/python
# .venv/bin/python
```

Вам **не нужно** вручную создавать окружение или активировать его для работы
через `uv run`. Все происходит прозрачно.

!!! tip "Что дальше по маршруту"
    После базового понимания окружений переходите к
    [Управлению зависимостями](06-dependencies.md), а затем к
    [Sync-workflow](07-sync-workflow.md), где подробно разбираются `uv lock` и `uv sync`.

!!! warning "Не коммитьте .venv в git"
    Директория `.venv` содержит бинарные файлы интерпретатора и установленные
    пакеты. Она не должна попадать в систему контроля версий. Убедитесь, что
    `.venv` добавлена в `.gitignore`:

    ```gitignore
    # .gitignore
    .venv/
    ```

    При выполнении `uv init` файл `.gitignore` с этой записью создается
    автоматически. Если `.gitignore` уже существует, `uv init` не изменяет
    его - убедитесь, что `.venv/` добавлена вручную.

## uv venv - создание окружения вручную

Хотя `uv` создает окружение автоматически, иногда требуется явный контроль.
Команда `uv venv` позволяет создать виртуальное окружение с нужными параметрами.

### Базовое использование

```bash
# Создание .venv с версией Python по умолчанию
uv venv

# Создание .venv с конкретной версией Python
uv venv --python 3.11

# Создание окружения с другим именем директории
uv venv myenv

# Создание с конкретной версией и другим именем
uv venv --python 3.12 .venv-3.12
```

Флаг `--seed` устанавливает `pip` и `setuptools` в создаваемое окружение.
Это полезно для legacy-инструментов, которые вызывают `pip` изнутри окружения:

```bash
uv venv --seed .venv
```

!!! warning "uv всегда по умолчанию работает с `.venv`"
    Все команды `uv` (`uv sync`, `uv run`, `uv add`) по умолчанию ищут и
    используют окружение `.venv` в корне проекта. Кастомно-именованные
    окружения (`.venv-3.11`, `myenv`) **не обнаруживаются автоматически** -
    для работы с ними нужно каждый раз явно задавать переменную `VIRTUAL_ENV`.

    Способы указать другое окружение:

    - `VIRTUAL_ENV=.venv-3.11 uv sync` - разовое указание для конкретной команды.
    - [direnv](https://direnv.net/) - утилита, которая автоматически устанавливает переменные
      окружения (включая `VIRTUAL_ENV`) при входе в директорию проекта.
      Достаточно создать файл `.envrc` с нужным значением `VIRTUAL_ENV`.
    - `UV_PROJECT_ENVIRONMENT` или `project-environment` в конфиге -
      постоянная настройка пути к окружению на уровне проекта
      (подробнее - в разделе [UV_PROJECT_ENVIRONMENT](#uv_project_environment---пользовательский-путь-к-окружению)).

### Контроль источника Python

Параметр `--python-preference` определяет, откуда `uv` возьмет интерпретатор:

```bash
# Использовать только managed-версии Python
uv venv --python-preference only-managed

# Предпочитать системный Python, если доступен
uv venv --python-preference system

# Использовать только системный Python (ошибка, если не найден)
uv venv --python-preference only-system
```

### Когда нужно создавать окружение вручную

| Сценарий | Автоматическое (.venv) | Ручное (uv venv) |
| -------- | ---------------------- | ---------------- |
| Обычная работа с проектом | Достаточно | Не требуется |
| Нужна конкретная версия Python | `uv sync` учтет `.python-version` | `uv venv --python 3.11` |
| Несколько окружений для тестов | Не подходит | `uv venv --python 3.X .venv-3.X` |
| Нестандартный путь к окружению | Через `UV_PROJECT_ENVIRONMENT` | `uv venv /path/to/env` |
| Окружение без привязки к проекту | Не подходит | `uv venv` в произвольном каталоге |

!!! tip "Для большинства случаев ручное создание не нужно"
    Если вы работаете с одним проектом и одной версией Python, автоматическое
    создание `.venv` через `uv sync` или `uv run` - оптимальный вариант. Ручное
    создание полезно для тестирования на нескольких версиях Python или для
    нестандартных конфигураций.

## Активация и деактивация

### Когда активация не нужна

При использовании `uv run` активация окружения **не требуется**. Команда
`uv run` сама находит `.venv`, подставляет правильный интерпретатор и выполняет
команду в контексте окружения:

```bash
# Активация не нужна - uv управляет всем сам
uv run python main.py
uv run pytest
uv run flask run
```

Это основной рекомендуемый способ запуска кода в проектах с uv.

### Когда активация нужна

В ряде ситуаций ручная активация все же необходима:

- **Интерактивная работа в терминале** - запуск `python`, `ipython`,
  произвольных команд без `uv run`.
- **Инструменты IDE** - VSCode/Cursor и PyCharm автоматически активируют
  `.venv` при открытии встроенного терминала (см. [Интеграция с IDE](#интеграция-с-ide)),
  после чего `python`, `pytest` и другие команды работают без `uv run`.
  Отладчик и запуск тестов через GUI тоже используют выбранный
  интерпретатор из `.venv`.
- **Скрипты, не знающие про uv** - CI-конвейеры или shell-скрипты,
  вызывающие `python` напрямую.

### Команды активации

=== "Linux / WSL 2 / macOS (bash/zsh)"

    ```bash
    source .venv/bin/activate
    ```

=== "Windows (cmd)"

    ```cmd
    .venv\Scripts\activate.bat
    ```

=== "Windows (PowerShell)"

    ```powershell
    .venv\Scripts\Activate.ps1
    ```

=== "fish"

    ```fish
    source .venv/bin/activate.fish
    ```

После активации приглашение терминала обычно меняется, показывая имя окружения:

```text
(.venv) user@host:~/my-app$
```

### Проверка активации

Чтобы убедиться, что окружение активировано, проверьте переменную `VIRTUAL_ENV`:

```bash
echo $VIRTUAL_ENV
# /home/user/my-app/.venv
```

Или проверьте путь к интерпретатору:

```bash
which python
# /home/user/my-app/.venv/bin/python
```

### Деактивация

Для выхода из виртуального окружения выполните:

```bash
deactivate
```

Команда `deactivate` доступна в любом shell после активации и возвращает
переменные окружения к исходному состоянию.

## Интеграция с IDE

Корректная настройка IDE позволяет пользоваться автодополнением, навигацией по
коду, подсветкой ошибок и встроенным отладчиком с учетом зависимостей проекта.

### VSCode / Cursor

VSCode и Cursor (основан на VSCode) автоматически обнаруживают `.venv` в корне
открытого проекта. В большинстве случаев настройка не требуется.

**Автоматическое обнаружение:**

1. Откройте каталог проекта (где находится `.venv`) в VSCode/Cursor.
2. Расширение Python автоматически обнаружит `.venv/bin/python` и предложит его
   как интерпретатор.
3. Подтвердите выбор в строке состояния (нижняя панель, слева).

**Ручная настройка (если автоопределение не сработало):**

Откройте настройки проекта `.vscode/settings.json` и укажите путь:

=== "Linux / WSL 2 / macOS"

    ```json
    {
        "python.defaultInterpreterPath": "${workspaceFolder}/.venv/bin/python"
    }
    ```

=== "Windows"

    ```json
    {
        "python.defaultInterpreterPath": "${workspaceFolder}\\.venv\\Scripts\\python.exe"
    }
    ```

**Автоматическая активация в терминале:**

VSCode может автоматически активировать `.venv` при открытии встроенного
терминала. Убедитесь, что в настройках включена опция:

```json
{
    "python.terminal.activateEnvironment": true
}
```

!!! tip "Выбор интерпретатора через Command Palette"
    Нажмите ++ctrl+shift+p++ (или ++cmd+shift+p++ на macOS) и введите
    `Python: Select Interpreter`. Выберите `.venv` из списка обнаруженных
    окружений.

### PyCharm

PyCharm также поддерживает `.venv` - как автоматически, так и с ручной
настройкой.

**Автоматическое обнаружение:**

При открытии проекта с `.venv` в корне PyCharm обычно предлагает использовать
найденный интерпретатор. Подтвердите предложение.

**Ручная настройка:**

1. Откройте **Settings** (++ctrl+alt+s++) -> **Project: <имя>** -> **Python Interpreter**.
2. Нажмите на шестеренку рядом с выпадающим списком -> **Add Local Interpreter**.
3. Выберите **Existing** и укажите путь:
   `.venv/bin/python` (Linux / WSL 2 / macOS) или
   `.venv\Scripts\python.exe` (Windows).
4. Нажмите **OK** и дождитесь индексации.

**Настройка для нового проекта:**

При создании нового проекта через PyCharm можно указать uv-managed интерпретатор:

1. В диалоге создания проекта выберите **Previously configured interpreter**.
2. Укажите путь к `.venv/bin/python` вашего uv-проекта.

!!! note "PyCharm и uv"
    Начиная с PyCharm 2024.2, IDE имеет встроенную поддержку `uv`. Если
    PyCharm обнаруживает `uv.lock` в проекте, он предложит использовать
    `uv` для управления зависимостями.

## UV_PROJECT_ENVIRONMENT - пользовательский путь к окружению

По умолчанию `uv` создает окружение в `.venv` внутри каталога проекта.
Переменная `UV_PROJECT_ENVIRONMENT` позволяет изменить это поведение.

!!! note "VIRTUAL_ENV vs UV_PROJECT_ENVIRONMENT"
    Эти переменные решают разные задачи:

    - `VIRTUAL_ENV` - разовое переключение окружения для конкретной команды
      (`VIRTUAL_ENV=.venv-3.11 uv sync`). Не сохраняется между вызовами.
    - `UV_PROJECT_ENVIRONMENT` (или `project-environment` в конфиге) -
      постоянная настройка пути к окружению на уровне проекта. Сохраняется
      в конфигурации и действует для всех команд.

### Настройка через переменную окружения

```bash
# Задать путь к окружению
export UV_PROJECT_ENVIRONMENT=/path/to/custom/venv

# Теперь uv sync и uv run используют этот путь
uv sync
```

### Настройка через конфигурацию проекта

=== "pyproject.toml"

    ```toml
    [tool.uv]
    project-environment = "/path/to/custom/venv"
    ```

=== "uv.toml"

    ```toml
    project-environment = "/path/to/custom/venv"
    ```

### Примеры использования

**Общее окружение для связанных проектов:**

```bash
# Оба сервиса используют одно окружение
export UV_PROJECT_ENVIRONMENT=~/shared-envs/microservices

cd service-a && uv sync
cd ../service-b && uv sync
```

**Размещение окружения вне проекта:**

```bash
# Хранить .venv за пределами дерева проекта
export UV_PROJECT_ENVIRONMENT=~/.virtualenvs/my-app

cd ~/projects/my-app
uv sync
```

!!! warning "Осторожно с общими окружениями"
    Общие окружения для разных проектов могут привести к конфликтам версий
    зависимостей. Используйте эту возможность только если вы точно понимаете,
    зачем это нужно.

## uv run vs ручная активация - сравнение

В повседневной работе вы можете выбирать между двумя подходами: запуском через
`uv run` или классической активацией окружения. У каждого есть свои сильные стороны.

### Сравнительная таблица

| Действие | uv run | Ручная активация |
| -------- | ------ | ---------------- |
| Запуск скрипта | `uv run python main.py` | `source .venv/bin/activate && python main.py` |
| Запуск тестов | `uv run pytest` | `source .venv/bin/activate && pytest` |
| Запуск линтера | `uv run ruff check .` | `source .venv/bin/activate && ruff check .` |
| Интерактивный REPL | `uv run python` | `source .venv/bin/activate && python` |
| Синхронизация зависимостей | Автоматически перед запуском | Вручную: `uv sync` |
| Переключение проектов | Не требует действий | `deactivate` -> `source .venv/bin/activate` |

### Рекомендации по выбору

**Используйте `uv run` когда:**

- Запускаете скрипты и команды из терминала
- Работаете в CI/CD конвейерах
- Переключаетесь между несколькими проектами
- Хотите гарантировать синхронизацию зависимостей перед запуском

**Используйте ручную активацию когда:**

- Работаете в интерактивном сеансе (REPL, отладка)
- IDE требует активированного окружения для отладчика
- Запускаете множество коротких команд подряд
- Используете инструменты, которые не знают про `uv`

!!! tip "Можно комбинировать"
    Ничто не мешает использовать оба подхода. Активируйте `.venv` для
    интерактивной работы в терминале IDE, а `uv run` используйте в скриптах и
    CI. Подходы не конфликтуют друг с другом.

## Несколько окружений в одном проекте

Иногда для одного проекта требуется несколько виртуальных окружений - например,
для тестирования совместимости с разными версиями Python.

### Создание окружений для разных версий Python

```bash
# Создание окружений для разных версий Python
uv venv --python 3.11 .venv-3.11
uv venv --python 3.12 .venv-3.12
uv venv --python 3.13 .venv-3.13
```

### Установка зависимостей в каждое окружение

Для установки зависимостей в кастомное окружение нужно явно указать его
через `VIRTUAL_ENV`. Без этой переменной `uv sync` будет работать с `.venv`:

```bash
# Установка зависимостей проекта в каждое окружение
VIRTUAL_ENV=.venv-3.11 uv sync
VIRTUAL_ENV=.venv-3.12 uv sync
VIRTUAL_ENV=.venv-3.13 uv sync
```

### Запуск тестов в каждом окружении

```bash
# Запуск тестов на каждой версии Python
VIRTUAL_ENV=.venv-3.11 uv run pytest
VIRTUAL_ENV=.venv-3.12 uv run pytest
VIRTUAL_ENV=.venv-3.13 uv run pytest
```

!!! note "Для матричного тестирования используйте CI"
    Если вам нужно регулярно тестировать проект на нескольких версиях Python,
    лучше настроить матрицу тестирования в CI (GitHub Actions, GitLab CI).
    Ручное создание нескольких окружений подходит для разовых проверок.

### Добавление окружений в .gitignore

Если вы используете нестандартные имена, не забудьте добавить их в `.gitignore`:

```gitignore
# .gitignore
.venv/
.venv-*/
```
