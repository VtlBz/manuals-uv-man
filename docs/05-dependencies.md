# Раздел 5. Управление зависимостями

---

## Базовые операции

Работа с зависимостями в uv основана на трехшаговой
модели. Каждая команда (`uv add`, `uv remove`)
выполняет три действия за один вызов:

1. Редактирует `pyproject.toml` (список зависимостей).
2. Пересчитывает `uv.lock` (граф зависимостей).
3. Синхронизирует `.venv` (устанавливает или удаляет
   пакеты).

При необходимости шаги можно выполнить отдельно:
отредактировать `pyproject.toml` вручную, затем
запустить `uv lock` и `uv sync`. Но в повседневной
работе достаточно `uv add` / `uv remove` - они
сделают все три шага автоматически.

### Добавление зависимостей

Команда `uv add` - основной способ добавления зависимостей. Она выполняет сразу
три действия:

1. Обновляет `pyproject.toml` (добавляет пакет в список зависимостей).
2. Пересоздает `uv.lock` (пересчитывает дерево зависимостей).
3. Синхронизирует `.venv` (устанавливает пакет в виртуальное окружение).

```bash
# Добавление одной зависимости
uv add requests

# Добавление с ограничением версии
uv add "requests>=2.28"

# Добавление нескольких пакетов сразу
uv add requests httpx pydantic

# Добавление пакета с extras
uv add "fastapi[standard]"
```

После выполнения `uv add requests` секция `[project]` в `pyproject.toml` будет
выглядеть так:

```toml
[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "requests>=2.32.3",
]
```

!!! note "Автоматическая нижняя граница версии"
    Когда вы пишете `uv add requests` без указания версии, uv добавляет
    constraint `>=` с текущей последней версией пакета. Это защищает от
    случайной установки устаревшей версии в будущем.

### Удаление зависимостей

```bash
# Удаление зависимости
uv remove requests
```

Команда `uv remove` выполняет обратные действия:

1. Удаляет пакет из `pyproject.toml`.
2. Пересчитывает `uv.lock` (убирает пакет и его неиспользуемые транзитивные
   зависимости).
3. Синхронизирует `.venv` (удаляет пакет из окружения).

### Инспекция зависимостей

Для просмотра установленных пакетов и их состояния
используются pip-совместимые команды:

```bash
# Плоский список установленных пакетов
uv pip list

# Пакеты, для которых доступны обновления
uv pip list --outdated

# Детали конкретного пакета (версия, лицензия, автор)
uv pip show requests
```

!!! note "`uv pip list` vs `uv tree`"
    `uv pip list` показывает плоский список пакетов
    в `.venv`. `uv tree` отображает иерархическое
    дерево зависимостей из `uv.lock`. Для диагностики
    "кто тянет пакет X" используйте
    `uv tree --invert`.

## Спецификаторы версий

Python-экосистема поддерживает несколько форматов ограничения версий. Понимание
каждого из них поможет правильно управлять зависимостями.

| Формат | Пример | Значение |
| ------ | ------ | -------- |
| `>=` | `>=2.28` | Версия 2.28 или выше |
| `>` | `>2.28` | Строго выше 2.28 (не включая) |
| `<` | `<3.0` | Строго ниже 3.0 |
| `>=,<` | `>=2.28,<3.0` | От 2.28 (включительно) до 3.0 (не включая) |
| `~=` | `~=2.28` | Compatible release: `>=2.28, <3.0` (эквивалент) |
| `==` | `==2.28.0` | Точная версия - только 2.28.0 |
| `==*` | `==2.28.*` | Wildcard: любой патч в пределах 2.28.x |
| `!=` | `!=2.29.0` | Любая версия, кроме 2.29.0 |
| `===` | `===2.28.0+local` | Точное совпадение строки (редко, не для PyPI) |

### Примеры использования

```bash
# Минимальная версия
uv add "requests>=2.28"

# Диапазон версий
uv add "requests>=2.28,<3.0"

# Совместимый релиз (эквивалент >=2.28,<3.0)
uv add "requests~=2.28"

# Точная версия (не рекомендуется в большинстве случаев)
uv add "requests==2.32.3"
```

!!! tip "Рекомендуемая стратегия"
    Для большинства зависимостей достаточно `>=`, которую uv добавляет
    автоматически. Используйте верхнюю границу (`<3.0`) только когда есть
    конкретная причина: например, известная несовместимость с новой мажорной
    версией.

### Lockfile фиксирует точные версии

Вне зависимости от того, какой спецификатор вы указали в `pyproject.toml`, в
`uv.lock` всегда записываются **точные** версии:

```toml
# pyproject.toml: flexible constraint
dependencies = ["requests>=2.28"]

# uv.lock: точная зафиксированная версия
[[package]]
name = "requests"
version = "2.32.3"
```

Это ключевое свойство lockfile: `pyproject.toml` описывает *допустимый
диапазон*, а `uv.lock` фиксирует *конкретную версию*, которая будет установлена.

### Конвертация Poetry -> PEP 440

При миграции с Poetry операторы версий необходимо
преобразовать в формат PEP 440:

| Poetry | PEP 440 | Пример |
| ------ | ------- | ------ |
| `^1.2.3` | `>=1.2.3,<2.0.0` | Совместимые мажорные |
| `^0.4.2` | `>=0.4.2,<0.5.0` | Для `0.x` - минорная граница |
| `~1.2.3` | `>=1.2.3,<1.3.0` | Совместимые минорные |
| `>=1.2.3` | `>=1.2.3` | Без изменений |
| `==1.2.3` | `==1.2.3` | Без изменений |
| `*` | без оператора | Любая версия |

!!! warning "Оператор `^` для версий 0.x"
    В Poetry `^0.4.2` означает `>=0.4.2, <0.5.0`
    (не `<1.0.0`). При миграции версий `0.x`
    будьте особенно внимательны - поведение
    отличается от обычного `^`.

## Нестандартные источники зависимостей

Не все зависимости размещены в PyPI. uv поддерживает
установку из git-репозиториев, по прямому URL и из
альтернативных индексов.

### Git-источники

```bash
# Главная ветка
uv add "git+https://github.com/encode/httpx.git"

# Конкретная ветка
uv add "git+https://github.com/encode/httpx.git@master"

# Конкретный тег
uv add "git+https://github.com/encode/httpx.git@0.27.0"

# Конкретный коммит (рекомендуется для воспроизводимости)
uv add "git+https://github.com/encode/httpx.git@a1b2c3d"

# Через SSH (приватные репозитории)
uv add "git+ssh://git@github.com/myorg/private.git"

# Подкаталог в монорепозитории
uv add "git+https://github.com/org/mono.git#subdirectory=packages/pkg"
```

Результат в `pyproject.toml`:

```toml
dependencies = [
    "httpx",
]

[tool.uv.sources]
httpx = { git = "https://github.com/encode/httpx.git", rev = "0.27.0" }
```

### URL-источники

Установка wheel-файла по прямому URL:

```bash
uv add "https://example.com/pkg-1.0-py3-none-any.whl"
```

```toml
[tool.uv.sources]
pkg = { url = "https://example.com/pkg-1.0-py3-none-any.whl" }
```

### Альтернативные индексы

Подключение приватного PyPI (Nexus, Artifactory,
GitLab Package Registry):

```toml
[[tool.uv.index]]
name = "internal"
url = "https://pypi.company.com/simple/"

[tool.uv.sources]
my-internal-lib = { index = "internal" }
```

Аутентификация через переменные окружения:

```bash
export UV_INDEX_INTERNAL_USERNAME="user"
export UV_INDEX_INTERNAL_PASSWORD="token"
```

Имя переменной строится по шаблону
`UV_INDEX_<NAME>_USERNAME` /
`UV_INDEX_<NAME>_PASSWORD`, где `<NAME>` - значение
поля `name` индекса в верхнем регистре.

## Группы зависимостей

В реальных проектах зависимости делятся на категории. Пользователям вашего
приложения не нужен `pytest`, а в production-окружении - `ruff`. uv
предоставляет несколько механизмов для такой организации.

### Production-зависимости: `[project.dependencies]`

Зависимости, необходимые для работы приложения:

```toml
[project]
dependencies = [
    "fastapi[standard]>=0.115",
    "pydantic>=2.0",
    "sqlalchemy>=2.0",
    "httpx>=0.27",
]
```

### Группы разработки: `[dependency-groups]` (PEP 735)

Стандарт [PEP 735](https://peps.python.org/pep-0735/) определяет формат групп
зависимостей для организации процесса разработки:

```toml
[dependency-groups]
dev = [
    "pytest>=8.0",
    "ruff>=0.8",
    "mypy>=1.13",
    "pre-commit>=4.0",
]
test = [
    "pytest>=8.0",
    "pytest-cov>=6.0",
    "pytest-asyncio>=0.24",
    "httpx>=0.27",
]
lint = [
    "ruff>=0.8",
    "mypy>=1.13",
]
docs = [
    "mkdocs-material>=9.5",
    "mkdocs-include-markdown-plugin>=7.0",
]
```

Команды для работы с группами:

```bash
# Добавление в группу dev по умолчанию
uv add --dev pytest

# Добавление в пользовательскую группу
uv add --group test pytest-cov

# Добавление в другую пользовательскую группу
uv add --group lint ruff
```

!!! note "Группа `dev` по умолчанию"
    При `uv sync` без дополнительных флагов uv устанавливает
    production-зависимости и группу `dev`. Остальные группы нужно запрашивать
    явно через `--group`.

### Опциональные зависимости: `[project.optional-dependencies]`

Extras предназначены для библиотек и позволяют конечным пользователям выбирать
функциональность:

```toml
[project.optional-dependencies]
ml = [
    "torch>=2.0",
    "transformers>=4.40",
    "numpy>=1.26",
]
postgres = [
    "asyncpg>=0.29",
    "psycopg[binary]>=3.1",
]
redis = [
    "redis>=5.0",
]
```

Добавление:

```bash
# Добавление в optional extras
uv add --optional ml torch
uv add --optional postgres asyncpg
```

### Сравнение с подходом pip-tools

При использовании `pip-tools` для каждой группы зависимостей требовалась пара
файлов:

```text
requirements.in        ->  requirements.txt
requirements-dev.in    ->  requirements-dev.txt
requirements-test.in   ->  requirements-test.txt
```

Каждый файл нужно компилировать отдельно (`pip-compile requirements-dev.in`),
следить за синхронизацией между файлами, разрешать конфликты вручную.

С uv все группы описаны в одном `pyproject.toml`, а весь граф зависимостей
зафиксирован в одном `uv.lock`. Конфликты между группами разрешаются
автоматически единым резолвером.

## `uv lock` - управление lockfile

Команда `uv lock` создает или обновляет файл `uv.lock`.

### Базовое использование

```bash
# Создание или обновление lockfile на основе pyproject.toml
uv lock
```

### Обновление зависимостей

```bash
# Обновление ВСЕХ зависимостей до последних допустимых версий
uv lock --upgrade

# Обновление только конкретного пакета
uv lock --upgrade-package requests

# Обновление нескольких конкретных пакетов
uv lock --upgrade-package requests --upgrade-package httpx
```

!!! warning "Разница между `uv lock` и `uv lock --upgrade`"
    - `uv lock` - пересчитывает lockfile, но сохраняет текущие версии, если они
      все еще удовлетворяют constraints. Новые версии появятся только для новых
      или измененных зависимостей.
    - `uv lock --upgrade` - игнорирует текущие pinned-версии и разрешает все
      зависимости заново, выбирая максимально новые допустимые версии.

### Стратегии разрешения зависимостей

uv поддерживает разные стратегии выбора версий. Настраивается через `[tool.uv]`
в `pyproject.toml`:

```toml
[tool.uv]
resolution = "highest"   # default
```

| Стратегия | Описание | Когда использовать |
| --------- | -------- | ------------------ |
| `highest` | Выбирает максимально новые версии (по умолчанию) | Стандартный выбор для большинства проектов |
| `lowest` | Выбирает минимально допустимые версии | Тестирование совместимости: "работает ли мой код с самыми старыми разрешенными версиями?" |
| `lowest-direct` | Минимальные версии для прямых зависимостей, максимальные - для транзитивных | Компромисс: проверка нижних границ без чрезмерного занижения транзитивных |

!!! example "Пример: зачем нужна стратегия `lowest`"
    Допустим, вы указали `requires-python = ">=3.10"` и
    `dependencies = ["pydantic>=2.0"]`. Стратегия `lowest` установит Pydantic
    2.0.0, а не последнюю 2.10.x. Это позволяет убедиться, что ваш код
    действительно совместим с минимальной заявленной версией.

## `uv sync` - синхронизация окружения

Команда `uv sync` приводит виртуальное окружение `.venv` в соответствие с
lockfile. Она устанавливает недостающие пакеты и удаляет лишние.

### Базовое использование uv sync

```bash
# Синхронизация окружения (включает группу dev по умолчанию)
uv sync
```

### Управление группами при синхронизации

```bash
# Пропустить dev-зависимости (для production-деплоя)
uv sync --no-dev

# Включить дополнительную группу
uv sync --group test

# Включить несколько дополнительных групп
uv sync --group test --group docs

# Установить только конкретную группу (без production-зависимостей)
uv sync --only-group lint

# Установить все группы
uv sync --all-groups
```

### Режимы для CI/CD

```bash
# Строгий режим: ошибка, если lockfile устарел
uv sync --locked

# Frozen-режим: пропустить проверку актуальности lockfile
uv sync --frozen
```

Подробное сравнение:

| Режим | Команда | Поведение | Сценарий |
| ----- | ------- | --------- | -------- |
| Обычный | `uv sync` | Обновляет lockfile при необходимости, затем устанавливает | Локальная разработка |
| Strict | `uv sync --locked` | Проверяет lockfile. Если не актуален - ошибка | CI: гарантия, что `uv.lock` обновлен |
| Frozen | `uv sync --frozen` | Устанавливает из lockfile без проверки | Docker-сборки, оффлайн |

!!! tip "Рекомендация для CI"
    Используйте `uv sync --locked` в CI-пайплайне. Если разработчик изменил
    `pyproject.toml`, но забыл выполнить `uv lock` и закоммитить обновленный
    `uv.lock`, сборка упадет с понятной ошибкой. Это дисциплинирует команду и
    предотвращает расхождения.

### Типичные комбинации

```bash
# CI: только production-зависимости, строгий режим
uv sync --locked --no-dev

# CI: установка всего для тестирования
uv sync --locked --group test

# Локально: установка всего, включая документацию
uv sync --all-groups

# Docker: frozen-установка production-зависимостей
uv sync --frozen --no-dev
```

## Стратегии обновления зависимостей

В долгоживущих проектах зависимости неизбежно
устаревают. Существует три основных подхода
к их обновлению.

### Реактивный (по требованию)

Обновление конкретного пакета при обнаружении
security-уязвимости или потребности в новой фиче:

```bash
uv lock --upgrade-package <пакет>
uv sync
```

**Плюсы:** минимальный риск, точечные изменения.
**Минусы:** уязвимости могут долго оставаться
незамеченными.

### Регулярный (по расписанию)

Обновление всех зависимостей по расписанию (раз
в спринт или раз в месяц):

```bash
uv lock --upgrade
uv sync
# прогнать тесты, проверить diff uv.lock
```

**Плюсы:** зависимости не копят техдолг.
**Минусы:** большой diff при редких обновлениях,
возможны регрессии.

### Автоматизированный (Renovate / Dependabot)

Инструменты (Renovate, Dependabot, Mend)
автоматически создают PR с обновлениями зависимостей.
Разработчик только ревьюит и мержит.

**Плюсы:** минимум ручной работы, быстрое обнаружение
уязвимостей.
**Минусы:** требует настройки CI и дисциплины ревью.

!!! tip "Рекомендация"
    Для приложений в production: реактивный +
    регулярный (раз в месяц). Для библиотек:
    реактивный, поскольку `uv.lock` обычно не
    коммитится.

## `uv tree` - визуализация дерева зависимостей

Команда `uv tree` показывает полное дерево зависимостей проекта, включая все
транзитивные зависимости.

### Прямое дерево

```bash
uv tree
```

Пример вывода:

```text
myapp v0.1.0
├── fastapi[standard] v0.115.6
│   ├── anyio v4.7.0
│   │   ├── idna v3.10
│   │   └── sniffio v1.3.1
│   ├── pydantic v2.10.4
│   │   ├── annotated-types v0.7.0
│   │   └── pydantic-core v2.27.2
│   ├── starlette v0.41.3
│   │   └── anyio v4.7.0 (*)
│   └── uvicorn[standard] v0.34.0
│       ├── httptools v0.6.4
│       └── uvloop v0.21.0
├── httpx v0.28.1
│   ├── anyio v4.7.0 (*)
│   ├── certifi v2024.12.14
│   ├── httpcore v1.0.7
│   └── idna v3.10 (*)
└── pydantic v2.10.4 (*)
```

### Инвертированное дерево

Показывает, кто зависит от конкретного пакета:

```bash
# Показать кто от чего зависит (обратное дерево)
uv tree --invert
```

Пример вывода:

```text
idna v3.10
├── anyio v4.7.0
│   ├── fastapi v0.115.6
│   │   └── myapp v0.1.0
│   ├── httpx v0.28.1
│   │   └── myapp v0.1.0
│   └── starlette v0.41.3
│       └── fastapi v0.115.6 (*)
└── httpx v0.28.1 (*)
```

### Дерево для конкретного пакета

```bash
# Показать дерево зависимостей для конкретного пакета
uv tree --package requests
```

!!! tip "Когда пригодится `uv tree`"
    - Поиск причин конфликтов версий: `uv tree --invert` покажет, какие пакеты
      требуют разные версии одной зависимости.
    - Аудит безопасности: проверка, какие пакеты тянут уязвимую транзитивную
      зависимость.
    - Оптимизация размера: определение "тяжелых" транзитивных зависимостей.

## Overrides и Constraints

Иногда стандартное разрешение зависимостей не дает нужного результата. Для таких
случаев uv предоставляет механизмы ручного управления.

### Override-зависимости

`override-dependencies` заставляет резолвер использовать указанную версию,
игнорируя constraints других пакетов:

```toml
[tool.uv]
override-dependencies = [
    "urllib3>=2.0",
]
```

!!! warning "Используйте overrides осторожно"
    Override может привести к несовместимости: если пакет A требует
    `urllib3<2.0`, а вы форсируете `>=2.0`, пакет A может работать некорректно.
    Применяйте overrides только когда точно знаете, что конфликт безопасен
    (например, constraint устарел, а пакет на самом деле совместим).

### Constraint-зависимости

`constraint-dependencies` добавляет ограничения на версии без установки самих
пакетов:

```toml
[tool.uv]
constraint-dependencies = [
    "numpy<2.0",
]
```

Это полезно, когда:

- Вы знаете, что `numpy>=2.0` ломает совместимость с одной из ваших
  зависимостей, но сам `numpy` является транзитивной зависимостью и не
  перечислен в `[project.dependencies]`.
- Вы хотите ограничить версию транзитивной зависимости, не добавляя ее в прямые
  зависимости.

### Сравнение override и constraint

| Механизм | Что делает | Уровень силы |
| -------- | ---------- | ------------ |
| `override-dependencies` | Заменяет constraints **всех** пакетов на указанный | Максимальный - игнорирует чужие требования |
| `constraint-dependencies` | Добавляет **дополнительное** ограничение поверх существующих | Мягкий - может привести к ошибке разрешения, если несовместим |

!!! example "Пример: конфликт транзитивных зависимостей"
    Ситуация: пакет `lib-a` требует `urllib3>=1.26,<2.0`, а пакет `lib-b`
    требует `urllib3>=2.0`. uv не сможет разрешить этот конфликт автоматически.

    Если вы точно знаете, что `lib-a` работает с `urllib3>=2.0` (просто не
    обновил свои constraints), можно использовать override:

    ```toml
    [tool.uv]
    override-dependencies = [
        "urllib3>=2.0",
    ]
    ```
