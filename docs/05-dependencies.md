# Раздел 5. Управление зависимостями

---

## Базовые операции

Работа с зависимостями в uv основана на трехшаговой модели. Каждая команда
(`uv add`, `uv remove`) выполняет три действия за один вызов:

1. Редактирует `pyproject.toml` (список зависимостей).
2. Пересчитывает `uv.lock` (граф зависимостей).
3. Синхронизирует `.venv` (устанавливает или удаляет пакеты).

При необходимости шаги можно выполнить отдельно: отредактировать `pyproject.toml`
вручную, затем запустить `uv lock` и `uv sync`. Но в повседневной работе достаточно
`uv add` / `uv remove` - они сделают все три шага автоматически.

### Добавление зависимостей

Команда `uv add` - основной способ добавления зависимостей. Она выполняет сразу
три действия:

1. Обновляет `pyproject.toml` (добавляет пакет в список зависимостей).
2. Пересоздает `uv.lock` (пересчитывает дерево зависимостей).
3. Синхронизирует `.venv` (устанавливает пакет в виртуальное окружение).

```bash
# Добавление одной зависимости
uv add requests

# Добавление с ограничением версии
uv add "requests>=2.33"

# Добавление нескольких пакетов с разными ограничениями
uv add requests "httpx>=0.28" "pydantic>=2.0,<3.0"

# Добавление пакета с extras
uv add "fastapi[standard]"
```

После выполнения `uv add requests` секция `[project]` в `pyproject.toml` будет
выглядеть так:

```toml
[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "requests>=2.33.1",
]
```

!!! note "Автоматическая нижняя граница версии"
    Когда вы пишете `uv add requests` без указания версии, uv добавляет
    constraint `>=` с текущей последней версией пакета. Это защищает от
    случайной установки устаревшей версии в будущем.

### Удаление зависимостей

```bash
# Удаление зависимости
uv remove requests
```

Команда `uv remove` выполняет обратные действия:

1. Удаляет пакет из `pyproject.toml`.
2. Пересчитывает `uv.lock` (убирает пакет и его неиспользуемые транзитивные зависимости).
3. Синхронизирует `.venv` (удаляет пакет из окружения).

### Инспекция зависимостей

Для просмотра установленных пакетов и их состояния
используются pip-совместимые команды:

```bash
# Плоский список установленных пакетов
uv pip list

# Пакеты, для которых доступны обновления
uv pip list --outdated

# Детали конкретного пакета (версия, лицензия, автор)
uv pip show requests
```

!!! note "`uv pip list` vs `uv tree`"
    `uv pip list` показывает плоский список пакетов в `.venv`. `uv tree`
    отображает иерархическое дерево зависимостей из `uv.lock`. Для
    диагностики "кто тянет пакет X" используйте `uv tree --invert`.

## Спецификаторы версий

Python-экосистема поддерживает несколько форматов ограничения версий.
Понимание каждого из них поможет правильно управлять зависимостями.

| Формат | Пример | Значение |
| ------ | ------ | -------- |
| `>=` | `>=2.28` | Версия 2.28 или выше |
| `>` | `>2.28` | Строго выше 2.28 (не включая) |
| `<` | `<3.0` | Строго ниже 3.0 |
| `>=,<` | `>=2.28,<3.0` | От 2.28 (включительно) до 3.0 (не включая) |
| `~=` | `~=2.28` | Compatible release: `>=2.28, <3.0` (эквивалент) |
| `==` | `==2.28.0` | Точная версия - только 2.28.0 |
| `==*` | `==2.28.*` | Wildcard: любой патч в пределах 2.28.x |
| `!=` | `!=2.29.0` | Любая версия, кроме 2.29.0 |
| `===` | `===2.28.0+local` | Точное совпадение строки, включая local-сегмент. Используется для внутренних сборок (приватные регистри, локальные wheel), т.к. PyPI не поддерживает local-версии |

### Примеры использования

```bash
# Минимальная версия
uv add "requests>=2.33"

# Диапазон версий
uv add "requests>=2.33,<3.0"

# Совместимый релиз (эквивалент >=2.33,<3.0)
uv add "requests~=2.33"

# Точная версия (не рекомендуется в большинстве случаев)
uv add "requests==2.33.1"
```

!!! tip "Рекомендуемая стратегия"
    Для большинства зависимостей достаточно `>=`, которую uv добавляет
    автоматически. Используйте верхнюю границу (`<3.0`) только когда есть
    конкретная причина: например, известная несовместимость с новой
    мажорной версией.

### Lockfile фиксирует точные версии

Вне зависимости от того, какой спецификатор вы указали в `pyproject.toml`, в
`uv.lock` всегда записываются **точные** версии:

```toml
# pyproject.toml: flexible constraint
dependencies = ["requests>=2.33"]

# uv.lock: точная зафиксированная версия
[[package]]
name = "requests"
version = "2.33.1"
```

Разделение ролей между двумя файлами:

- `pyproject.toml` - **допустимый диапазон** версий,
  поддерживаемых проектом (`>=2.33`).
- `uv.lock` - **точная фиксация** конкретной версии (`2.32.3`)
  для воспроизводимости: все участники проекта и CI получают
  одинаковые зависимости.

Если нужно обновить зафиксированную версию:

```bash
# Обновить все зависимости до новейших допустимых
uv lock --upgrade

# Обновить конкретный пакет
uv lock --upgrade-package requests

# Применить обновленный lockfile
uv sync
```

Обновленный `uv.lock` коммитится в репозиторий.

### Конвертация Poetry -> PEP 440

При миграции с Poetry операторы версий необходимо преобразовать в формат PEP 440:

| Poetry | PEP 440 | Пример |
| ------ | ------- | ------ |
| `^1.2.3` | `>=1.2.3,<2.0.0` | Совместимые мажорные |
| `^0.4.2` | `>=0.4.2,<0.5.0` | Для `0.x` - минорная граница |
| `~1.2.3` | `>=1.2.3,<1.3.0` | Совместимые минорные |
| `>=1.2.3` | `>=1.2.3` | Без изменений |
| `==1.2.3` | `==1.2.3` | Без изменений |
| `*` | без оператора | Любая версия |

!!! warning "Оператор `^` для версий 0.x"
    В Poetry `^0.4.2` означает `>=0.4.2, <0.5.0` (не `<1.0.0`).
    При миграции версий `0.x` будьте особенно внимательны -
    поведение отличается от обычного `^`.

## Нестандартные источники зависимостей

Не все зависимости размещены в PyPI. `uv` поддерживает установку
из git-репозиториев, по прямому URL и из альтернативных индексов.

!!! warning "Sources - только в `pyproject.toml`"
    Секция `[tool.uv.sources]` всегда читается из `pyproject.toml`,
    даже при наличии `uv.toml`. Это сделано намеренно - источники
    зависимостей привязаны к проекту и должны быть одинаковы на
    всех машинах. Подробнее о конфигурации см. раздел [Источники зависимостей `[tool.uv.sources]`](09-configuration.md#источники-зависимостей-tooluvsources).

### Git-источники

```bash
# Главная ветка
uv add "git+https://github.com/encode/httpx.git"

# Конкретная ветка
uv add "git+https://github.com/encode/httpx.git@master"

# Конкретный тег
uv add "git+https://github.com/encode/httpx.git@0.28.0"

# Конкретный коммит (рекомендуется для воспроизводимости)
uv add "git+https://github.com/encode/httpx.git@a1b2c3d"

# Через SSH (приватные репозитории)
uv add "git+ssh://git@github.com/myorg/private.git"

# Подкаталог в монорепозитории
uv add "git+https://github.com/org/mono.git#subdirectory=packages/pkg"
```

В CLI после `@` указывается любой git-ref - `uv` сам определяет,
тег это, ветка или коммит. При ручном редактировании `pyproject.toml`
нужно явно выбрать ключ:

| Ключ | Что указывает | Пример значения |
| ---- | ------------- | --------------- |
| `tag` | Git-тег (имя релиза) | `"v1.2.0"`, `"0.28.0"` |
| `branch` | Ветка | `"main"`, `"develop"` |
| `rev` | Конкретный коммит (SHA) | `"a1b2c3d4e5f6"` |

Примеры записи в `pyproject.toml`:

```toml
[project]
dependencies = [
    "httpx",
    "my-lib",
    "experiments",
]

[tool.uv.sources]
httpx = { git = "https://github.com/encode/httpx.git", tag = "0.28.0" }
my-lib = { git = "https://github.com/company/my-lib.git", branch = "develop" }
experiments = { git = "https://github.com/user/exp.git", rev = "a1b2c3d4" }
```

!!! tip "Воспроизводимость"
    `tag` и `branch` могут измениться со временем (тег можно переставить,
    ветка обновляется). Для максимальной воспроизводимости используйте
    `rev` с полным SHA коммита.

### URL-источники

Установка пакета по прямому URL. Поддерживаемые форматы:
`.whl` (wheel), `.tar.gz` и `.zip` (source distribution).

```bash
uv add "https://example.com/pkg-1.0-py3-none-any.whl"
```

```toml
[tool.uv.sources]
pkg = { url = "https://example.com/pkg-1.0-py3-none-any.whl" }
```

### Локальные источники (path)

Установка из локального пути - директории с `pyproject.toml`
или готового файла (`.whl`, `.tar.gz`, `.zip`):

```bash
# Директория с проектом
uv add --editable ../shared-utils

# Локальный wheel-файл
uv add "../dist/my_lib-1.0-py3-none-any.whl"
```

```toml
[tool.uv.sources]
shared-utils = { path = "../shared-utils", editable = true }
my-lib = { path = "../dist/my_lib-1.0-py3-none-any.whl" }
```

Флаг `--editable` / `editable = true` доступен только для директорий
с проектом - изменения в исходном коде сразу видны без переустановки.
Для файлов (`.whl`, `.tar.gz`, `.zip`) editable-установка невозможна.

### Альтернативные индексы

`uv` поддерживает подключение дополнительных индексов (приватных регистри,
например Nexus, Artifactory, GitLab Package Registry и др.).

По умолчанию PyPI является **дефолтным индексом** - он опрашивается последним,
если пакет не найден в других индексах. Объявление индекса с `default = true`
**заменяет PyPI** на указанный регистри. **Дефолтный индекс может быть только один**.

Порядок поиска пакетов:

1. Дополнительные индексы - в порядке объявления в конфигурации.
2. Дефолтный индекс (PyPI или заменивший его) - всегда последний.

Поведение индекса определяют флаги:

| Флаг | Поведение |
| ---- | --------- |
| (без флагов) | Дополнительный индекс: поиск всех пакетов (PyPI остается) |
| `explicit = true` | Только для поиска пакетов, явно привязанных через `[sources]` |
| `default = true` | Заменяет PyPI как дефолтный (может быть только один) |

Ниже - типовые сценарии подключения.

**1. Дополнительный индекс** (PyPI + корпоративный):

=== "pyproject.toml"

    ```toml
    [[tool.uv.index]]
    name = "company"
    url = "https://pypi.company.com/simple/"
    ```

=== "uv.toml"

    ```toml
    [[index]]
    name = "company"
    url = "https://pypi.company.com/simple/"
    ```

Поиск: `company` -> PyPI. Публичные пакеты по-прежнему загружаются с PyPI,
корпоративные - из `company`.

**2. Полная замена PyPI** (закрытая сеть, корпоративные правила):

=== "pyproject.toml"

    ```toml
    [[tool.uv.index]]
    name = "company"
    url = "https://pypi.company.com/simple/"
    default = true
    ```

=== "uv.toml"

    ```toml
    [[index]]
    name = "company"
    url = "https://pypi.company.com/simple/"
    default = true
    ```

PyPI полностью отключен. Все пакеты (включая публичные) должны быть доступны
в корпоративном регистри. Обращений к `pypi.org` не будет.

**3. Специализированный индекс** (PyTorch, CUDA):

=== "pyproject.toml"

    ```toml
    [[tool.uv.index]]
    name = "pytorch"
    url = "https://download.pytorch.org/whl/cu118"
    explicit = true

    [tool.uv.sources]
    torch = { index = "pytorch" }
    torchvision = { index = "pytorch" }
    ```

=== "uv.toml"

    ```toml
    [[index]]
    name = "pytorch"
    url = "https://download.pytorch.org/whl/cu118"
    explicit = true

    [sources]
    torch = { index = "pytorch" }
    torchvision = { index = "pytorch" }
    ```

`torch` и `torchvision` загружаются только из `pytorch`. Остальные пакеты -
с PyPI. Флаг `explicit` защищает от случайной установки пакетов из
специализированного индекса.

**4. Комбинация** (корпоративный + специализированный + PyPI):

=== "pyproject.toml"

    ```toml
    [[tool.uv.index]]
    name = "company"
    url = "https://pypi.company.com/simple/"

    [[tool.uv.index]]
    name = "pytorch"
    url = "https://download.pytorch.org/whl/cu118"
    explicit = true

    [tool.uv.sources]
    torch = { index = "pytorch" }
    ```

=== "uv.toml"

    ```toml
    [[index]]
    name = "company"
    url = "https://pypi.company.com/simple/"

    [[index]]
    name = "pytorch"
    url = "https://download.pytorch.org/whl/cu118"
    explicit = true

    [sources]
    torch = { index = "pytorch" }
    ```

Поиск: `torch` -> только `pytorch`; остальные пакеты -> `company` -> PyPI.

Приватные регистри обычно требуют аутентификацию.
`uv` поддерживает несколько способов: переменные окружения, файл `.netrc`,
интеграцию с `keyring`. Подробная настройка аутентификации с примерами
для каждого способа - в [разделе 9](09-configuration.md).

## Группы зависимостей

В реальных проектах зависимости делятся на категории. Пользователям вашего
приложения не нужен `pytest`, а в production-окружении - `ruff`. `uv`
предоставляет несколько механизмов для такой организации.

### Production-зависимости: `[project.dependencies]`

Зависимости, необходимые для работы приложения:

```toml
[project]
dependencies = [
    "fastapi[standard]>=0.136",
    "pydantic>=2.0",
    "sqlalchemy>=2.0",
    "httpx>=0.28",
]
```

### Группы разработки: `[dependency-groups]` (PEP 735)

Стандарт [PEP 735](https://peps.python.org/pep-0735/) определяет формат групп
зависимостей для организации процесса разработки:

```toml
[dependency-groups]
dev = [
    "pytest>=9.0",
    "ruff>=0.15",
    "mypy>=2.0",
    "pre-commit>=4.6",
]
test = [
    "pytest>=9.0",
    "pytest-cov>=7.1",
    "pytest-asyncio>=1.3",
    "httpx>=0.28",
]
lint = [
    "ruff>=0.15",
    "mypy>=2.0",
]
docs = [
    "mkdocs-material>=9.7",
    "mkdocs-include-markdown-plugin>=7.2",
]
```

Команды для работы с группами:

```bash
# Добавление в группу dev по умолчанию
uv add --dev pytest

# Добавление в пользовательскую группу
uv add --group test pytest-cov

# Добавление в другую пользовательскую группу
uv add --group lint ruff
```

### Настройка `default-groups`

По умолчанию `uv sync` устанавливает `[project.dependencies]` и группы,
перечисленные в настройке `default-groups`. Если `default-groups` не задан,
включается только группа `dev`.

Чтобы `uv sync` по умолчанию устанавливал несколько групп,
укажите их в `default-groups`:

=== "pyproject.toml"

    ```toml
    [tool.uv]
    default-groups = ["dev", "test"]
    ```

=== "uv.toml"

    ```toml
    default-groups = ["dev", "test"]
    ```

Если нужно, чтобы `uv sync` по умолчанию ставил только production-зависимости
без дополнительных групп - явно задайте пустой список: `default-groups = []`.

Флаги `--group`, `--no-dev` и `--only-group` действуют только
на текущий запуск и не изменяют `pyproject.toml`.

!!! warning "Флаг `--no-dev` отключает **все** default-группы"
    Несмотря на название, `--no-dev` отключает не только группу
    `dev`, а **все** группы из `default-groups`. Если
    `default-groups = ["dev", "lint"]`, то `uv sync --no-dev`
    пропустит и `dev`, и `lint`. Чтобы оставить отдельные группы,
    комбинируйте: `uv sync --no-dev --group lint`.

Полный набор команд для управления группами при синхронизации -
ниже в разделе `uv sync`.

### Опциональные зависимости: `[project.optional-dependencies]`

Extras предназначены для библиотек и позволяют конечным пользователям выбирать
функциональность:

```toml
[project.optional-dependencies]
ml = [
    "torch>=2.11",
    "transformers>=5.8",
    "numpy>=2.4",
]
postgres = [
    "asyncpg>=0.31",
    "psycopg[binary]>=3.3",
]
redis = [
    "redis>=7.4",
]
```

Добавление:

```bash
# Добавление в optional extras
uv add --optional ml torch
uv add --optional postgres asyncpg
```

### Сравнение с подходом pip-tools

При использовании `pip-tools` для каждой группы зависимостей требовалась пара
файлов:

```text
requirements.in        ->  requirements.txt
requirements-dev.in    ->  requirements-dev.txt
requirements-test.in   ->  requirements-test.txt
```

Каждый файл нужно компилировать отдельно (`pip-compile requirements-dev.in`),
следить за синхронизацией между файлами, разрешать конфликты вручную.

С `uv` все группы описаны в одном `pyproject.toml`, а весь граф зависимостей
зафиксирован в одном `uv.lock`. Конфликты между группами разрешаются
автоматически единым резолвером.

## Синхронизация и lockfile

Управление lockfile (`uv lock`) и синхронизация окружения (`uv sync`)
подробно описаны в [разделе 6](06-sync-workflow.md). Здесь - краткая
сводка ключевых команд:

| Задача | Команда |
| ------ | ------- |
| Пересчитать lockfile | `uv lock` |
| Обновить все зависимости | `uv lock --upgrade` |
| Обновить конкретный пакет | `uv lock --upgrade-package <pkg>` |
| Синхронизировать окружение | `uv sync` |
| Только production | `uv sync --no-dev` |
| Строгий режим (CI) | `uv sync --locked` |

## Стратегии обновления зависимостей

В долгоживущих проектах зависимости неизбежно устаревают.
Существует три основных подхода к их обновлению.

### Реактивный (по требованию)

Обновление конкретного пакета при обнаружении
security-уязвимости или потребности в новой фиче:

```bash
uv lock --upgrade-package <пакет>
uv sync
```

**Плюсы:** минимальный риск, точечные изменения.
**Минусы:** уязвимости могут долго оставаться
незамеченными.

### Регулярный (по расписанию)

Обновление всех зависимостей по расписанию (раз
в спринт или раз в месяц):

```bash
uv lock --upgrade
uv sync
# прогнать тесты, проверить diff uv.lock
```

**Плюсы:** зависимости не копят техдолг.
**Минусы:** большой diff при редких обновлениях, возможны регрессии.

### Автоматизированный (Renovate / Dependabot)

Инструменты (Renovate, Dependabot, Mend) автоматически создают PR
с обновлениями зависимостей. Разработчик только ревьюит и мержит.

**Плюсы:** минимум ручной работы, быстрое обнаружение уязвимостей.
**Минусы:** требует настройки CI и дисциплины ревью.

!!! tip "Рекомендация"
    Для приложений в production: реактивный + регулярный (раз в месяц).
    Для библиотек: реактивный, поскольку `uv.lock` обычно не коммитится.

Показывает, кто зависит от конкретного пакета:

```bash
# Показать кто от чего зависит (обратное дерево)
uv tree --invert
```

Пример вывода:

```text

├── anyio v4.7.0
```

```bash
# Показать дерево зависимостей для конкретного пакета
```

!!! tip "Когда пригодится `uv tree`"
    - Поиск причин конфликтов версий: `uv tree --invert` покажет, какие пакеты
      требуют разные версии одной зависимости.
    - Аудит безопасности: проверка, какие пакеты тянут уязвимую транзитивную
      зависимость.
    - Оптимизация размера: определение "тяжелых" транзитивных зависимостей.

## Overrides и Constraints

Иногда стандартное разрешение зависимостей не дает нужного результата. Для таких
случаев `uv` предоставляет механизмы ручного управления.

### Override-зависимости

`override-dependencies` заставляет резолвер использовать указанную версию,
игнорируя constraints других пакетов:

=== "pyproject.toml"

    ```toml
    [tool.uv]
    override-dependencies = [
        "urllib3>=2.0",
    ]
    ```

=== "uv.toml"

    ```toml
    override-dependencies = [
        "urllib3>=2.0",
    ]
    ```

!!! warning "Используйте overrides осторожно"
    Override может привести к несовместимости: если пакет A требует
    `urllib3<2.0`, а вы форсируете `>=2.0`, пакет A может работать некорректно.
    Применяйте overrides только когда точно знаете, что конфликт безопасен
    (например, constraint устарел, а пакет на самом деле совместим).

### Constraint-зависимости

`constraint-dependencies` добавляет ограничения на версии без установки самих
пакетов:

=== "pyproject.toml"

    ```toml
    [tool.uv]
    constraint-dependencies = [
        "numpy<2.0",
    ]
    ```

=== "uv.toml"

    ```toml
    constraint-dependencies = [
        "numpy<2.0",
    ]
    ```

Это полезно, когда:

- Вы знаете, что `numpy>=2.0` ломает совместимость с одной из ваших
  зависимостей, но сам `numpy` является транзитивной зависимостью и не
  перечислен в `[project.dependencies]`.
- Вы хотите ограничить версию транзитивной зависимости, не добавляя ее в прямые
  зависимости.

### Сравнение override и constraint

| Механизм | Что делает | Уровень силы |
| -------- | ---------- | ------------ |
| `override-dependencies` | Заменяет constraints **всех** пакетов на указанный | Максимальный - игнорирует чужие требования |
| `constraint-dependencies` | Добавляет **дополнительное** ограничение поверх существующих | Мягкий - может привести к ошибке разрешения, если несовместим |

!!! example "Пример: конфликт транзитивных зависимостей"
    Ситуация: пакет `lib-a` требует `urllib3>=1.26,<2.0`, а пакет `lib-b`
    требует `urllib3>=2.0`. `uv` не сможет разрешить этот конфликт автоматически.

    Если вы точно знаете, что `lib-a` работает с `urllib3>=2.0` (просто не
    обновил свои constraints), можно использовать override:

    === "pyproject.toml"

        ```toml
        [tool.uv]
        override-dependencies = [
            "urllib3>=2.0",
        ]
        ```

    === "uv.toml"

        ```toml
        override-dependencies = [
            "urllib3>=2.0",
        ]
        ```
